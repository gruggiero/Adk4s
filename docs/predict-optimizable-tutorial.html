    Predictors you can read, address and rewrite

    Phase 0 of the DSPy port adds one thing to ADK4S: a way for a program that nobody wrote yet to enumerate the LM-call sites inside a program that somebody else wrote, read their prompts as data, and hand back a new program with one of them changed. This page explains why that matters, how it is built in Scala 3, how it differs from the Python original, and — in detail — how a PureScala model in the verified module is tied to the shipped code so the two provably describe the same traversal.

Phase 1 (adk4s-eval) is in flight — see §10.

    1 · Why prompts have to become data

    An LLM step in almost every codebase looks like a function. You write a prompt, you interpolate some variables, you parse the answer. In ADK4S today that is StructuredLLM.function[I, A]: give it a PromptTemplate[I] and a Schema[A], get back an I => F[A]. Excellent ergonomics, and completely opaque: once the template is a function, nothing can look inside it, and nothing can produce a different one.

    DSPy's contribution is not a prompting trick. It is the observation that the instruction string and the few-shot examples attached to each LM call are parameters — the same kind of thing as weights — and that if you can (a) score a whole program against data and (b) mechanically rewrite those parameters, then you can search for better ones. "Compile" a program once against a training set, save the resulting instructions and demos as an artifact, and serve that. Their headline economic claim follows: small model + compiled prompts often beats big model + hand-written prompts.

    The split that organises everything

    Forward pass — render a prompt, call the model, parse the answer, run tools, stream. ADK4S already has this, and in places (SAP's type-aware coercion, Smithy schemas, Constraint.check) it is stronger than DSPy's.

    Backward pass — score the program, propose new parameters, keep what wins. ADK4S has none of it. Everything in the port plan (docs/dspy-port-operative-plan.md) is the backward pass, and every part of it needs the same primitive: enumerate the tunable sites of an arbitrary program and replace one.

    That primitive is what Phase 0 builds, and nothing else. No optimizer, no demo rendering, no persistence, no trace capture. The reason for spiking it alone is stated bluntly in the proposal: the surface is load-bearing for Phases 2–4 and effectively irreversible once optimizers are written against it. Get the shape wrong and every optimizer fights the types forever.

    Two words you need before anything else

    Predictor — one LM-call site. Not the model, not the client: the site, with its own instruction string and its own few-shot examples. A program has several; a RAG pipeline has a query-rewriter and an answerer; each is a predictor with its own tunable text.

    Program — a value composed of predictors and other programs. In Python that is an object whose attributes happen to be modules. In Scala it is a case class whose fields happen to be predictors. The optimizer must work on both without knowing either type.

    2 · Predict: an LM call site with state

    In DSPy, Predict is the atom: it holds a signature (instructions + typed input/output fields) and a mutable demos list that optimizers write into. Calling it renders the signature and demos through an adapter, calls the LM, and coerces the reply back to the declared types.

    Phase 0 of the ADK4S port deliberately ships a placeholder, Predict0, and says so in its name. It carries exactly the state an optimizer needs and exposes no way to run anything — because a Phase 0 that could render demos into prompts would be a Phase 2 that shipped untested.

    adk4s-optimize/src/main/scala/org/adk4s/optimize/Predict0.scalafinal case class Predict0[F[_], I, O](
  state:      PredictorState,        // the tunable part — instructions, demos, frozen
  template:   PromptTemplate[I],     // the carried capability …
  schema:     Schema[O],             // … not invoked in Phase 0
  structured: StructuredLLM[F]
)

object Predict0:
  given hasPredictorStateForPredict0[F[_], I, O]: HasPredictorState[Predict0[F, I, O]] with
    def state(self: Predict0[F, I, O]): PredictorState = self.state
    def withState(self: Predict0[F, I, O], s: PredictorState): Predict0[F, I, O] =
      self.copy(state = s)

    The tunable part is one small immutable record:

    final case class Demo(input: ujson.Value, output: ujson.Value)

final case class PredictorState(
  instructions: String,        // the one string an instruction optimizer rewrites
  demos:        Vector[Demo],  // what BootstrapFewShot fills in
  frozen:       Boolean        // DSPy's `_compiled` — "optimizers, hands off"
)
    Three design commitments hiding in that record
    • Instructions live on the state, not on the module. The same contract can run under a plain predictor, a chain-of-thought wrapper, or a future agent wrapper, and an optimizer still has exactly one string to rewrite.
    • Demos are JSON, not typed values. An optimizer holding a heterogeneous program cannot know I and O; ujson.Value is the erased currency. The type safety is restored at render time in Phase 2.
    • Frozen is data, not a type. A frozen predictor is a perfectly ordinary value you can construct. That keeps freeze a pure function instead of a phantom-typed ceremony — and it means the "don't touch frozen" rule must be enforced by the surface's own behaviour, which is why it shows up in the laws and in the formal model.

    Field names and descriptions are deliberately not tunable. DSPy calls this the inert-field rule: callers depend on the field names, so optimizers may never touch them. In Scala the rule is free — the fields are the case-class types, and the erased surface simply has no method that could change them.

    3 · Optimizable: the three actions

    An optimizer is generic in the program type. It sees no Predict0, no I/O, no user case classes — only paths and states. That is the whole surface:

    adk4s-optimize/src/main/scala/org/adk4s/optimize/Optimizable.scalatrait Optimizable[P]:
  /** every tunable site, in field declaration order */
  def predictors(p: P): Vector[(PredictorPath, PredictorState)]

  /** total variant: typed error instead of an exception */
  def updateEither(p: P, path: PredictorPath, f: PredictorState => PredictorState)
      : Either[OptimizeError, P]

  /** convenience: raises the same typed error from the Left branch */
  def update(p: P, path: PredictorPath, f: PredictorState => PredictorState): P

  /** every non-frozen site at once */
  def updateAll(p: P, f: (PredictorPath, PredictorState) => PredictorState): P =
    predictors(p).filter(!_._2.frozen).foldLeft(p) { (acc, entry) =>
      val (path, _) = entry
      update(acc, path, s => f(path, s))
    }

    Addresses are plain strings, outermost first — case-class field names, and for collections the element index rendered as a string:

    final case class PredictorPath(segments: Vector[String]):
  def render: String = segments.mkString(".")   // "rag.answer", "steps.2"

enum OptimizeError extends Throwable:
  case UnknownPath(path: PredictorPath)   // not a site this program has
  case FrozenPath(path: PredictorPath)    // a site that said "hands off"

    Note what updateAll's default implementation gives you for free: frozen exclusion is structural. It is a filter before a fold, not a runtime check inside the update, so there is no code path in which f is applied to a frozen state. A reviewer can see this in four lines; a Python if not p._compiled: scattered across an optimizer cannot be audited that way.

    The laws that make an optimizer an optimizer

    Phase 0 also ships OptimizerLaws in main scope (the pattern already used by AgentMemoryLaws), so every optimizer written in Phases 2–4 can be held to the same three statements:

    LawStatementWhat it rules out
    Puritythe student value is unchanged after compile the DSPy hazard of one candidate mutating another through a shared sub-module
    Frozen-preservedfrozen states are bit-identical in the result an optimizer that "helpfully" retunes a site the user pinned
    Path-set-preservedthe result has the same path set as the student an optimizer that changes program structure — optimizers tune state, never shape

    The two toy optimizers in Phase 0 exist only to prove the surface survives contact with structurally different optimizer shapes: UppercaseInstructions rewrites every instruction string, StaticDemoInjector appends a fixed demo. Different data, same updateAll, same derived instance, zero knowledge of the program type. That is the acceptance test for the entire phase.

      5 · Same idea, different machine: DSPy vs ADK4S

      DSPy's equivalent of Optimizable is named_predictors(), which walks self.__dict__ at runtime, recursing into lists and dicts, collecting anything that is a Predict. Forking a candidate is a hand-written deepcopy. Freezing is a _compiled boolean the optimizer is expected to honour.

        super().__init__()                       # ProgramMeta enforces this call
        self.rewrite = dspy.Predict("q -> q2")
        self.answer  = dspy.ChainOfThought("ctx, q -> a")

      The advantage, stated plainly

      Python's dynamism was doing real work here, and Scala cannot copy the technique — but it does not need the technique. What DSPy achieves with a runtime walk plus a deepcopy plus a convention, ADK4S achieves with a compile-time walk plus a value plus a typed error. The optimizer loop becomes referentially transparent, which is what makes the three laws testable at all, and what makes the algorithm small enough to state in a theorem prover.

      And the cost, equally plainly
      • Existentials leak into optimizer internals. A program's predictors have different I/O; the surface erases them to PredictorState + ujson.Value. That is the deliberate trade — and the reason the surface is frozen by proposal rather than evolved casually.
      • Only what the derivation knows about is reachable. Predictors behind a Map, an Option, or a bespoke container are invisible until a later phase teaches the derivation about them. DSPy's walk would have found them.
      • Derivation errors are compiler errors, and inline-expansion errors are not famous for their readability. See the deep dive below for one real scar.

      6 · How the derivation actually works

      Optimizable.derived is an inline def that walks the product mirror at compile time. There are three parallel sequences: the field types (m.MirroredElemTypes, a tuple type), the field labels (m.MirroredElemLabels, constant string types), and the runtime field values (productIterator). The types drive the inline recursion; the labels become path segments; the values are what actually gets read and rebuilt.

      private inline def predictorsWalk[Types <: Tuple](
  values: Vector[Any], names: List[String], prefix: Vector[String]
): Vector[(PredictorPath, PredictorState)] =
  inline erasedValue[Types] match
    case _: EmptyTuple     => Vector.empty
    case _: (head *: tail) =>
      val contributed = predictField[head](values.head, prefix :+ names.head)
      contributed ++ predictorsWalk[tail](values.tail, names.tail, prefix)

      Per field, the rule is a four-way decision, and its order is load-bearing:

      1. Vector[elem] → indexed leaves, one per element, segment = the index as a string. (Matched first, structurally, because a Vector never has an Optimizable instance of its own.)
      2. otherwise summonFrom:
        • an Optimizable[T] in scope → sub-program: recurse, prefixing the field name to every nested path;
        • else a HasPredictorState[T] → leaf: one entry, path = field name;
        • else → skip. Not a fallback, not a silent failure: a field with neither instance is not a tunable site, and skipping it is the specified behaviour.

      Optimizable is tried before HasPredictorState so that a type which is both a program and a predictor is treated as a subtree. In Phase 0 nothing is both, but the ordering is fixed now because Phase 2's real Predict could be.

      The update side, and one honest scar

      updateEither walks the same fields looking for the one whose name equals path.segments(0), then either applies f (leaf), recurses with the remaining segments (sub-program), or indexes into the collection. The rebuilt program comes back through the mirror:

      updateWalk[m.MirroredElemTypes](fieldValues, fieldNames, Vector.empty, path, f).map { updated =>
  val tuple: Tuple = updated.foldLeft(EmptyTuple: Tuple)((acc, v) => acc :* v.asInstanceOf[Object])
  m.fromTuple(tuple.asInstanceOf[m.MirroredElemTypes])
}
      Deep dive — why the Vector update path resolves its typeclass through a closure implementation

      In predictCollection, the HasPredictorState[Elem] instance is summoned at the top of the inline expansion, and everything works. In the update path the same summonFrom sat after a runtime if/else, at a greater inline depth, where the pattern-bound element type no longer resolved.

      The fix in the shipped code is deliberate and documented: a helper predictCollectionWithUpdater[Elem] is called before any runtime branching, and returns, per element, a triple of (path, state, updater closure) where the closure has already captured the typeclass instance:

      val updater: PredictorState => Any = s => leaf.withState(e.asInstanceOf[Elem], s)

      The subsequent runtime code (updateCollectionFromEntries) is then plain Scala: find the entry whose path matches exactly, check frozen, apply f, call the updater, rebuild the vector with updated(idx, …). This is why the entries are computed even on the branch that turns out not to need them — moving that call inside the branch is what breaks, so the comment above it says exactly that.

      Cost: a small amount of wasted work per non-matching field. Benefit: the collection case resolves at all. It is the sort of thing worth reading before Phase 2 touches this file.

      Where the error cases come from

      Every UnknownPath in the implementation corresponds to a structural impossibility, and each is a separate arm rather than a catch-all: empty path; no field with that name; a leaf addressed with extra segments; a sub-program addressed without them; a Vector addressed without an index; an index out of range. FrozenPath has exactly two sites — the leaf branch and the collection branch. Ring 8's adversarial review of this change specifically hunted for a case _ => p that would have swallowed any of them.

      A detail worth knowing before Phase 2

      The sub-program branch propagates the inner Left unchanged (subOpt.updateEither(field, subPath, f).map(…)), so an error raised inside a nested program carries the relative path: addressing sub.leaf on a frozen nested predictor returns FrozenPath(leaf), not FrozenPath(sub.leaf). The playground above reproduces that faithfully rather than tidying it up. It costs nothing today — nothing consumes the payload — but a GEPA-style optimizer logging failed writes by path will want the absolute one.

      8 · Ring 6: the verified-mirror pattern

      This repository grades changes by verification rings. Ring 6 is formal verification with Stainless. The first draft of this change's design.md declared Ring 6 not applicable, with three reasons: the code uses Mirror and inline; it carries ujson.Value; and Stainless is pinned to Scala 3.7.2 while the module builds on 3.8.4.

      That reasoning was then rejected — and the rejection is the interesting part. All three facts are statements about the types the shipped code mentions. None is a statement about the algorithm. Strip the algorithm to its observable effect and what remains is a pre-order traversal of a finite tree, which is exactly the kind of thing a prover eats for breakfast. Hence schema v10's verified-mirror pattern: don't verify the shipped code, verify a faithful model of its algorithm, and then bind the model to the shipped code with a property test that runs both.

      The abstraction

      Shipped codeModelWhy that is faithful
      a program value (case class of fields)Sub(fields: List[Prog])field declaration order becomes list order — and declaration order is the law under proof
      a Predict0 fieldPred(frozen: Boolean, state: BigInt)the only observable properties of a state, for this algorithm, are "is it frozen" and "is it this one"
      a non-predictor fieldPlain()it exists, it occupies a declaration position, it is never enumerated
      Vector[Predict0]Coll(elems: List[Prog])ordered, index-addressed
      PredictorPath("outer","leaf")List[BigInt] of child indicesnames are resolved to positions by the bridge; the traversal only ever cares about position
      instructions, demos, ujson— (erased to the BigInt)the traversal never inspects them; carrying them would prove nothing extra

      The model is 200 lines of PureScala in the leaf verified module (Scala 3.7.2, not aggregated by the root build, depends on nothing project-local):

      verified/src/main/scala/org/adk4s/verified/PredictorKernel.scalasealed abstract class Prog
case class Pred(frozen: Boolean, state: BigInt) extends Prog
case class Plain()                              extends Prog
case class Sub(fields: List[Prog])              extends Prog
case class Coll(elems: List[Prog])              extends Prog

def pathsImpl(p: Prog, prefix: List[BigInt], startIdx: BigInt): List[List[BigInt]] = {
  decreases(p)
  p match {
    case Pred(_, _) => List(prefix)
    case Plain()    => Nil[List[BigInt]]()
    case Sub(fs)    => fs match {
      case Nil()      => Nil[List[BigInt]]()
      case Cons(h, t) =>
        pathsImpl(h, prefix ++ Cons(startIdx, Nil()), BigInt(0)) ++
        pathsImpl(Sub(t), prefix, startIdx + BigInt(1))          // ← tail re-wrapped as a Prog
    }
    case Coll(es)   => /* same shape */
  }
}

def updateAll(p: Prog, f: BigInt => BigInt): Prog = {
  decreases(p)
  p match {
    case Pred(fr, st) => if (fr) Pred(fr, st) else Pred(fr, f(st))   // frozen: bit-identical
    case Plain()      => Plain()
    case Sub(fs)      => Sub(updateAllList(fs, f))
    case Coll(es)     => Coll(updateAllList(es, f))
  }
}
      The trick in the recursion — and its price

      Look at pathsImpl(Sub(t), prefix, startIdx + 1). The natural way to walk a list of children is a helper that recurses on the list; but then Stainless must compare a tree measure with a list measure, which are incomparable, and every such call produces an unprovable termination obligation. Re-wrapping the tail as Sub(t) makes every recursive call tree→tree, so the default ADT size measure applies uniformly.

      It very nearly works. The default ProgPrimitiveSize measure does not recurse into list contents, so Sub(Cons(h,t)) and Sub(t) can measure the same to the solver — and those are exactly the seven obligations that still come back invalid below. The functions do terminate; the default measure cannot see why.

      Read this before quoting "Ring 6 passed"

      Two gaps separate the current state from the spec's stated ambition, and both are visible in the ledger:

      1. Seven termination obligations are still invalid. They are all "measure decreases" on the re-wrapped tail calls (countPreds ×2, frozenStates ×2, pathsImpl ×2, updateAllList ×1). Closing them needs an explicit treeSize measure that counts list contents, or a newer Stainless with better measure inference.
      2. The four semantic lemmas generate no obligations at all. pathsCompleteness, updateAllShapePreserved, updateAllFrozenPreserved and roundTripIdentity are written as plain boolean functions without ensuring clauses — a deliberate retreat, recorded in the commit message, after the smt-z3 subprocess fallback hung on the postconditions. The native Z3 interface is unavailable because ScalaZ3 is not built for Scala 3. So the meanings those lemmas express are currently checked by the bridge property test, not by the prover.

      What Stainless does establish today: the model's matches are exhaustive, its measures are non-negative, and 28 of 35 obligations — including every updateAll termination obligation — discharge. That is real, and it is less than "the contracts are proven". The spec's own delegation rule applies: a diverging obligation moves into the delegation table with a named Ring 3 property, and is never silently dropped.

      What closing gap 2 would look like next step

      Restore the postconditions on the recursive functions and give the prover a measure it can actually use:

      def treeSize(p: Prog): BigInt = {
  decreases(p)
  p match
    case Pred(_, _) => BigInt(1)
    case Plain()    => BigInt(1)
    case Sub(fs)    => BigInt(1) + listSize(fs)
    case Coll(es)   => BigInt(1) + listSize(es)
}.ensuring(_ > BigInt(0))

def pathsImpl(p: Prog, prefix: List[BigInt], startIdx: BigInt): List[List[BigInt]] = {
  decreases(treeSize(p))                        // explicit, counts list contents
  …
}.ensuring(_.size == countPreds(p))             // the completeness contract, back on the function

      Then either build ScalaZ3 for Scala 3.7.2 and drop the jar on the classpath (the native interface, which is what the postconditions need for tolerable performance), or move to a Stainless release whose measure inference handles ADTs containing lists. Until one of those lands, the honest label for Ring 6 on this change is partial.

      9 · The bridge: why the model is the same algorithm

      A proof about a model you also wrote is worth nothing on its own — the classic failure of formal methods is proving something true about a program you do not ship. The verified-mirror pattern's answer is the bridge: a property test in the shipped module that runs the real Optimizable and the model PredictorKernel on the same generated programs and asserts they agree, on exactly the invariants the model is supposed to carry.

      adk4s-optimize/src/test/scala/org/adk4s/optimize/PredictorModelBridgeSpec.scalaproperty("bridge-paths-match: Pipeline collection"):

    // field names and index strings → child indices, then compare element-for-element
    realIndexChains ==== modelIndexChains

      Six properties make up the bridge: path-sequence equality for each of the three derivation shapes (leaf, nested sub-program, collection), path-set preservation after updateAll, frozen-state identity, and round-trip identity. Build wiring is one line — adk4s-optimize dependsOn(verified % Test) — and it works only in that direction, because TASTy is backward compatible: a 3.8.4 module can read the 3.7.2 artifact, never the reverse. That is also why verified depends on nothing project-local. stainlessEnabled := false by default, so sbt test pays a plain compile of the model and the solver only runs under the explicit ring6 alias.

      What the bridge does and does not buy

      Catches: any drift between the shipped traversal and the proven one that shows up in path order, path membership, or frozen identity — which is to say, every structural bug the model's contracts are about. Try the first four injections: each turns the bridge red within a handful of generated programs.

      Does not catch: the broadcast injection. Writing every element of a Vector preserves the path set, preserves frozen identity when no sibling is frozen, and preserves order — so the bridge stays green while the update is wrong. That bug belongs to a different guard, and the spec names it: Ring 3's update-only-target property. This is the delegation discipline in action — every law that the model cannot carry is written down with the property that carries it instead, rather than being quietly assumed.

      Read down that column and the honest sentence is: we are sure the shipped traversal and the modelled traversal are the same traversal (link 3, empirically, over generated programs), and we are sure the model is total and terminating on most of its call sites (link 1); we are not yet sure, by proof, that the traversal means what the contracts say — that part still rests on properties, not on Z3. Which is a considerably stronger position than "we wrote tests", and a considerably weaker one than "it is verified". Saying which of the two you have is the entire point of keeping the ledger.

      adk4s-eval/src/main/scala/org/adk4s/eval/{Metric,Trace,TraceEntry}.scalatrait Metric[F[_], I, O]:
  /** `None` in evaluation mode; `Some(trace)` when an optimizer is calling.
    * This signature is FROZEN — Phase 2/3 optimizers depend on it. */
  def apply(gold: Example[I, O], pred: O, trace: Option[Trace]): F[Score]

final case class TraceEntry(path: String, input: ujson.Value, output: ujson.Value)

final case class Trace(entries: Vector[TraceEntry]):
  /** GEPA's `pred_trace`: the slice belonging to one predictor */
  def forPredictor(path: String): Trace =
    Trace(entries.filter(entry => entry.path.startsWith(path)))
      Two modules that must meet, and deliberately cannot see each other

      TraceEntry.path is a bare String, not a PredictorPath — and Trace.forPredictor is a prefix filter, which is exactly the shape PredictorPath.render produces ("rag.answer", "steps.2"). The two modules are joined by that string convention and by nothing else: the build comment on adk4s-eval spells out the Ring 2 purity rule — it must not depend on adk4s-optimize, and adk4s-optimize does not depend on it either.

      They meet in Phase 2, in a third place: BootstrapFewShot takes a Metric from eval and an Optimizable from optimize, runs a program under a TraceCollector, and converts each passing trace entry into a Demo credited to the predictor at that entry's path. The String/PredictorPath seam is the one place where a rename could silently break the credit assignment — worth a typed bridge when Phase 2 wires them together.

      The frozen Option[Trace] argument is the same discipline as the frozen predictor surface, applied one module over: pin the signature before anything consumes it, so the consumers (a demo optimizer, then a reflective one) never force a change to a contract that many call sites already depend on. DSPy's equivalent is a five-argument duck-typed convention discovered at runtime; here it is one method, and the "am I being evaluated or optimized?" toggle is a value of type Option.

      What each remaining phase needs from the surface

      PhaseNeeds from this surface
      1 · eval core — in flightnothing structural. Its only tie to Phase 0 is the trace-path string convention above, and the Evaluate harness every later optimizer scores candidates with.
      2 · compiler MVPpredictors to mint demos per site; updateAll to attach them; PredictorState as the unit of CompiledState save/load. The real Predict replaces Predict0 by implementing the same HasPredictorState, and derived instances keep working untouched.
      3 · instruction optimizationCOPRO and GEPA rewrite exactly one field of PredictorState; PredictorPath.render feeds Trace.forPredictor, which is already written and waiting
      4 · orchestrationan Optimizable instance for graphs and for ReactAgent (system prompt as instructions, tool descriptions as pseudo-predictors) — the acceptance test being that optimizers need no changes at all

      Two open items are already named for later phases rather than discovered later: Map[String, *] recursion in the derivation (deferred from Phase 0), and the module direction question — Demo, PredictorState, PredictorPath and HasPredictorState are expected to move into structured-llm in Phase 2 so that Signature can carry demos without inverting the module graph.

      Checkpoint

      The three sentences worth keeping
      1. An optimizer is a function from a program to a program that may change predictor state and nothing else; the surface exists to make "and nothing else" checkable.
      2. Python found predictors by walking objects at runtime; Scala finds them by walking a mirror at compile time, and gets purity, ordering and typed errors as a side effect rather than as a discipline.
      3. You cannot verify code that uses inline, Mirror and JSON — but you can verify the traversal underneath it and then bind the two with a property test. The binding is the load-bearing part; without it the proof is about a program you do not ship.
