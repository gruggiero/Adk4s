    Chapter 4 · Architecture of knowledge

    The two ledgers

    A workflow that writes specs across months needs an answer to two different questions: “does this type already exist?” and “what is the stable name for the behaviour I am changing?” They sound similar. They need completely different data structures, and conflating them is why most documentation rots.

    The problem: two kinds of forgetting

    Watch what goes wrong without either ledger. Both failures are mundane and both compound.

    Forgetting types

    Spec 7 needs an identifier for a run. There is already RunId in core.types, but the agent doesn't know, so it creates RunIdentifier in orchestration.model. Six months later you have four near-identical types, three conversion functions between them, and a bug that lives in the conversion.

    Forgetting behaviour

    Spec 12 says “AgentRunner.resume must re-emit the checkpoint event”. Later a refactor renames the class to ResumableRunner and moves the method. The spec is now wrong — it references a symbol that no longer exists — but nothing tells you, because prose doesn't compile.

    verified-scala3 keeps two ledgers, deliberately separate, each optimised for one of these:

    Ledger one · the type inventory

    A project-scoped living document listing every domain type: refined/opaque types with their constraints, sealed traits and enums with their variants, case classes with field types, service traits with their methods and their implementations, IDL models, property generators. 

    ## Sealed Traits and Enums

| Type | Kind | Variants | Package | Introduced By |
|------|------|----------|---------|---------------|
| `AgentEvent` | sealed trait | MessageOutput, ToolCallRequested, … | `org.adk4s.core.interrupt` | pre-existing |
| `RunResult`  | sealed trait | Completed, Interrupted, Failed      | `org.adk4s.orchestration.agent` | pre-existing |

## Service Traits

| Trait | Type Param | Methods | Implementations | Package | Introduced By |
|-------|-----------|---------|-----------------|---------|---------------|
| `AgentMemory` | F[_] | remember, recall, rememberAll | FileBackedAgentMemory, InMemoryAgentMemory | `org.adk4s.memory` | spec:add-memory-api/store |

    Three properties that make it work

    It is project-scoped, not per-change. This sounds like filing trivia; it is the difference between a living document and a dead one. When each change kept its own copy, every new change re-scanned from scratch and the Introduced By provenance — the audit trail saying which spec created this type — was reset to “found by a scan”. The knowledge died at every archive boundary.

    It is verified, not regenerated. Each change writes a thin inventory-check.md report that confirms rows still match the code and fixes stale ones preserving their provenance. A from-scratch rescan is forbidden precisely because it would overwrite spec:add-memory-api/store with scan:AgentMemory.scala.

    It is built by a parser. The scanner parses sources with Scalameta rather than matching text, which matters more than it sounds.

    Failure mode · the regex inventory

    An earlier version of this scanner used regular expressions. It catalogued the words consolidates, definitions, prefixing, value and values as sealed types — they appeared in comments after the word “sealed”. It also missed every nested declaration and, on a multi-module build, silently found zero concepts because it only looked at a top-level src/ that did not exist. A parser cannot make either mistake: a comment is not a declaration, and a nested enum is a tree node with a parent.

    Deep dive · what “nested” means for namingoptional

    An enum declared inside an object is not called FallbackSemantic by the compiler — it is RunnableOps.FallbackSemantic. The scanner reports the qualified form, matching how Metals and SemanticDB name it. That is not pedantry: it means an inventory row can be pasted directly into a semantic query (chapter 9) and resolve. When the inventory and the code-intelligence tools disagree about names, every automated cross-check between them silently degrades.

    Similarly, the Implementations column is built by linking extends clauses across files, including anonymous implementations (new Retriever[F]: … inside a factory), which are reported as MemoryRetriever (anonymous). A trait's implementations are the first thing you need when a spec changes its contract.

    Ledger two · the behavioural registry

    The second ledger answers a question types cannot: what does this system do, in the user's vocabulary, independent of how it is currently built?

    Prior art · concept design

    The registry follows Meng & Jackson, “What You See Is What It Does: A Structural Pattern for Legible Software” (arXiv:2508.14511). A concept is an independent unit of user-facing functionality with a purpose, its own state, a set of actions, and an operational principle. The pattern's sharpest rule: concepts never reference each other. Cross-concept behaviour is expressed separately as synchronizations — declarative when / where / then rules. The lineage runs back through Jackson's problem frames and Alloy; the modularity intuition will feel familiar from Parnas.

    Each concept is one markdown file with four parts:

    concept MemoryAwareRunner
purpose
    Decorate an AgentRunner with opt-in memory awareness: recall relevant
    facts before each turn and persist new episodes after completed turns,
    without changing the underlying runner's behavior when memory is absent.
state
    agentRunner: MemoryAwareRunner -> AgentRunner
    memory:      MemoryAwareRunner -> Option[AgentMemory[IO]]
    policy:      MemoryAwareRunner -> MemoryPolicy
actions
    run [ messages: List[Message] ; maxSteps: Int ]
        => [ result: RunResult.Completed(output, messages) ]
    run [ messages ; maxSteps ]
        => [ result: RunResult.Interrupted(checkpointId, signal) ]
    resume [ checkpointId: String ; results ; maxSteps ] => [ result: RunResult ]
operational principle
    A caller constructs a MemoryAwareRunner with a runner, an optional
    memory, and a policy. On run, the decorator first recalls the most
    relevant facts for the latest user input; if recall yields hits, a
    message with the rendered context is prepended before delegating…

    Then, crucially:

    ## Implementation map

| Element | Code |
|---|---|
| state    | `MemoryAwareRunner.memory` (`adk4s-orchestration/…/MemoryAwareRunner.scala`) |
| action `run` | `MemoryAwareRunner.run` → `MemoryHook.preTurn` → `postTurn` |
| runtime host | `adk4s-orchestration` |
    Rule · the Implementation map is the only place code identifiers live

    Specs reference behaviour as Concept/action. Class names, method names and file paths appear in exactly one place per concept — the Implementation map. A refactor therefore updates one table, not every spec that ever mentioned the type.

    Why this earns its keep: the altitude rule

    This is the payoff, and it is worth stating precisely. Compare two ways of writing the same requirement:

    Wrong altitude

    “When MemoryAwareRunner.runWithEvents calls MemoryHook.preTurn, the returned fs2.Stream[IO, AgentEvent] SHALL be forwarded unchanged.”

    Right altitude

    “MemoryAwareRunner/runWithEvents SHALL forward the underlying runner's event stream unchanged.” Implementation symbols go in ## Implementation Anchors at the bottom of the spec.

    The first version is wrong on the day someone renames the hook — and wrong silently, because nothing checks prose. The second stays true through any refactor that preserves behaviour, which is what a refactor is by definition. The archived spec still describes reality years later.

    Analogy · the menu and the kitchen

    A restaurant menu says “slow-braised beef, 6 hours”. It does not say “Marco puts the pot on the third burner”. When Marco leaves, the menu is still correct; only the kitchen rota changes. The behavioural registry is the menu; the Implementation map is the rota; the altitude rule is the policy that keeps burner numbers off the menu. And the reason customers — and specs — care: the promise is about what arrives, not who cooked it.

    Synchronizations: behaviour that spans concepts

    Since concepts never reference each other, cross-concept behaviour lives in named synchronizations: 

    sync RecallToContext
when   { MemoryAwareRunner/run: [ messages ] }
where  { memory is present and policy.recallK > 0 }
then   { AgentMemory/recall: [ latestUserInput ; recallK ] }

impl: `MemoryHook.preTurn` (`adk4s-orchestration/…/MemoryHook.scala`)
Deviation: best-effort — a recall failure is logged and the turn proceeds.

    Note the Deviation line. The registry is descriptive, not prescriptive: it records what the code actually does, including where that violates the pattern's own ideals. A registry that describes the system you wish you had is worse than none, because it silently becomes a second source of truth that disagrees with reality.

    The machine check

    Prose ledgers rot. This one has scanner/registry-check.sh — bash and git grep only (it predates the v12 prerequisite set and still needs nothing more), so it runs on any CI runner — making three passes:

    1. Symbols. Every backticked identifier in every Implementation map and impl: line still exists in the source tree. A row citing a file that also names symbols gets those symbols checked inside that file; a symbol that survives elsewhere is reported as a weak binding to tighten, not a failure.
    2. Fold fields. A state row may declare exactly which fields a fold populates (maps f1, f2, …); every listed field must appear in that file. This catches the declared-but-never-folded bug: a field present on the model shape that no code ever writes.
    3. Spec references. Every Concept/action cited by an active spec must be declared by a registry file, and the action must appear in that concept's actions block — not merely somewhere in the file's prose.
    Why it is designed this way · the anti-drift argument

    Documentation decays because nothing forces it to move when the code moves. The Implementation map inverts that: it is the single binding between behaviour and code, so keeping it correct is one table's worth of work, and a script fails the build when it is wrong. The cost of accuracy drops below the cost of inaccuracy — and that, not discipline, is what makes documentation survive.

    Two ledgers, three viewpoints

    If you know DDD, the behavioural registry is close to a ubiquitous language made machine-checkable, and concepts resemble bounded contexts scoped by user-facing purpose rather than by team.

    The addition DDD lacks: an Implementation map with a script that fails when the language and the code drift apart. The ubiquitous language usually degrades into a glossary nobody updates — for exactly the cost reason above.

    Think of the type inventory as a symbol table and the registry as a semantic model. The inventory is derived mechanically and answers name-resolution questions; the registry is authored and answers intent questions.

    Compilers keep both for the same reason this workflow does: you cannot recover intent from a symbol table, and you cannot resolve names from intent. The provenance column is the debug info — expensive to reconstruct, cheap to carry.

    As a library maintainer you already keep these implicitly: a public API surface (what may not break) and a changelog of behaviour (what changed for users). The inventory is the first; the registry plus specs are the second.

    The workflow's contribution is making the surface diffable — step 12 machine-diffs inventory snapshots to detect unplanned public API growth, which is the scope-creep check that keeps “while I was in there” out of your public types.

    When to adopt the registry

    The type inventory is mandatory; the behavioural registry is not, and the honest guidance is:

    • Adopt it when several specs touch the same behaviour over time, when refactors regularly invalidate old specs, or when the system has real domain vocabulary worth stabilising.
    • Skip it for a small library with one obvious API surface, or a short-lived project. Every registry-dependent rule (altitude, the step 0 registry gate, the spec-reference lint) is conditional on openspec/concepts/ existing.

    Bootstrapping is one-time: run the extraction skill against existing code, which produces concepts from persistent command/event enums, state structures, message consumers and transport entry points — and, valuably, surfaces the deviations it finds along the way.

    Check yourself

    A third thing also called a “ledger”, and it is not these two

    Chapter 12 introduces evidence-ledger.jsonl — an append-only log of ring commands actually run, with their exit codes. Same word, same append-only, provenance-carrying shape, but a different axis entirely: these two ledgers answer “what exists, and what is it called”, fixed at design time; the evidence ledger answers “was this specific claim actually checked, in this session”, written at verification time. Neither substitutes for the other — a concept can be correctly registered and still have a discharged clause nobody ever ran.
