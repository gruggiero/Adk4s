    Chapter 9 · Tools

    The tooling

    What is mechanical, what is judgement, and — the question that shapes every tool here — where must this be able to run? The answer to that last one explains why some checks are 200 lines of bash while others are a language server.

    The portability constraint

    Before any individual tool, the constraint that determines their design:

    Rule · the gate checks must run anywhere

    The gate checks depend on a declared prerequisite set (schema v12): bash, git, jq at runtime, plus shellcheck, bats, shfmt and openspec in CI — no JVM, no network, no artifact repository. They run on a restricted CI runner that cannot reach Maven Central. Portability is a correctness property for a gate: a check that only runs on a developer's laptop is a check that stops running. Before v12 the rule was zero-dependency (bash and git grep only); the reasoning is unchanged, but hand-rolled escaping and the absence of a test framework were where the defects lived, so the dependency set is now declared and installable rather than empty.

    Tools that need a compiler or an index (the scanner, the semantic recipes) are workstation-grade and therefore advisory — they make the agent and the human faster, but no gate depends on them. Keep that distinction clear as you read: it is the difference between a tool you may lose and a tool whose absence blocks a merge.

    The mechanical gate checks

    registry-check.sh — three passes over the behavioural registry

    $ scanner/registry-check.sh .
registry-check: OK (611 implementation-map tokens verified,
                    3 spec concept references checked,
                    2 weak binding(s) to tighten)
    1. Symbols. Every backticked identifier in every Implementation map still exists. When a row cites a file and symbols, the symbols are checked inside that file; a symbol that survives elsewhere is reported as a weak binding — a warning, not a failure, because rows legitimately mix an algebra's file with its implementations' symbols.
    2. Fold fields. maps f1, f2, … declarations are checked against the fold's source — the machine check for declared-but-never-folded state.
    3. Spec references. Every Concept/action cited by an active spec must be declared, and the action must appear in that concept's actions block — not merely somewhere in its prose. Concepts a spec marks as new are skipped until they exist.

    spec-lint.sh — the mechanical subset of the spec rules

    You have used its logic twice already (chapters 3 and 5 embed a port of it). Ten FAIL checks and seven warnings:

    CheckFires when
    F1requirement has no SHALL/MUST before its first **Given**
    F2a negative requirement (only/never/must not — in title or body) has no scenario
    F3property without a **Generator strategy** line
    F4requirements exist but no Proof Obligations section
    F5temporal property missing trigger or response event
    F6obligation Source names nothing resolvable
    F7a requirement no obligation names — unenforced
    F8a typed source (Property:/Scenario:) naming a heading that does not exist
    F9a code-shaped artifact that resolves to no tracked file — opt-in --artifacts, run post-implementation at Step 12
    F10a behavioural registry exists but a spec has no ## Concepts Used (behavioral) section — the structural half of the altitude rule
    W1–W5vague words · row-count shortfall · unconfirmed adversarial scenario · ordinal references · impossibility claim enforced only by tests
    W6Ring 6 declared with no obligation naming a bridge — a proof about a model nobody runs
    W7a code identifier inside a Given/When/Then clause — build command, source file, fully-qualified name, or a token the project's own ledgers class as code

    Note why F9 is opt-in rather than always on: a spec is written before its tests exist, so at planning time the artifact column is a commitment, and only after implementation is it a fact. Making it a default FAIL would break every new spec; making it unavailable would leave the last link of the obligation chain unchecked forever.

    The judgement checks — observability, testability, altitude compliance, type-feasibility — stay in the artifact instruction for a human or agent to apply. The script does not pretend to do them, which is why its clean run is meaningful.

    The CONTEXT block — why applicability is never judgement

    Several checks are conditional: check 17 applies only if the project has a behavioural registry, checks 3 and 18 only if a capability profile exists. It is tempting to file the whole check under “judgement” and move on. That is precisely the mistake, and it has a real instance.

    The failure · N/A by assumption

    A review marked the altitude rule N/A on a repository holding 30 concept files. The reviewer's own account of it was correct on every point: the script does not check altitude, the rule is a judgement check, the instruction says a human applies it. The reasoning was sound. It rested on a fact that was never looked up — “openspec/concepts/ probably doesn't exist here”.

    Notice the shape. Nothing failed loudly. The report said N/A, which reads like a considered verdict, and a silent skip is indistinguishable from a genuine non-applicability.

    So split the conditional check in two, and notice that the halves are different kinds of question:

    Does this rule apply here?

    A fact. A directory exists or it does not. There is a correct answer, it is one test -d away, and a reviewer who answers it from memory is guessing at something free to check.

    Does this spec obey it?

    A judgement. Is Episode in this sentence a domain word or a class name? That genuinely needs a reader, and no amount of bash will settle it.

    Only the second belongs to the reviewer. So spec-lint.sh now prints a CONTEXT block unconditionally — before any spec output, on every run — stating each conditional check's applicability: 

    spec-lint: CONTEXT — repository facts. These decide each conditional check's
           APPLICABILITY. Compliance remains yours; applicability does not.
  schema                openspec/schemas/verified-scala3  v11
  behavioural registry  openspec/concepts/             PRESENT (30 concepts)
    -> check 17 ALTITUDE **APPLIES**. "N/A" is not a valid verdict for it.
  type inventory        openspec/concept-inventory.md  PRESENT (125 typed rows)
    -> check 6 (reused concepts exist) **APPLIES**.
  capability profile    openspec/capability-profile.md PRESENT
    -> checks 3 and 18 **APPLY**
       deterministic test kit detected: TestControl
    The negative case is printed just as loudly

    On a repository with no registry the block says “check 17 ALTITUDE is N/A (attested by this script, not assumed)”. That sentence is the whole idea. N/A stops being something a reviewer concludes and becomes something a machine reports — and the report template requires the block pasted verbatim, so a verdict of N/A against a check the script says APPLIES is now a visible contradiction rather than an invisible gap.

    Generalise it, because this is not really about one rule:

    Rule · do not answer from memory what a script answers from the filesystem

    Every conditional rule's precondition is machine-supplied; only its compliance is judged. A reviewer asked to decide both will eventually decide the first one wrong, and — worse — will decide it wrong quietly, because a skipped check produces no output at all. Wherever a workflow says “if the project has X”, ask who determines X, and make it a program.

    Instruction drift — the field nobody read

    The same investigation turned up a second cause, and it is the more embarrassing one. Every skill carries a version stamp: 

    metadata:
  generatedBy: verified-scala3-schema/7.0.0

    That field sat frozen at 7.0.0 while the schema reached 11, and the copy actually installed in the agent's skill directory was older still — it stopped at check 12 and did not contain the altitude rule at all. An agent can follow its instructions perfectly and still miss a check that was added three versions after the instructions it holds.

    Recorded, but never checked

    This is the exact defect class the whole workflow exists to eliminate — the same shape as an obligation whose artifact was never written, or a laws suite that passes everything. A version field that nothing compares is decoration. spec-lint.sh now reads it, searching the common install roots, and prints INSTRUCTION DRIFT when the installed skill's schema version differs from the schema on disk. The remedy is boring; the point is that the discrepancy is no longer silent.

    danger-scan.sh — Ring 1's portable echo

    $ scanner/danger-scan.sh <baseline-SHA> [--also <importers>]
danger-scan: adk4s-core/src/main/scala/.../ToolsNode.scala
  [catch-all] 160:    case other => Some(ToolExecutionFailure(input, other))
  [unsafe-get] 88:    val cfg = config.get

    Scans the spec's production diff for the dangerous patterns from chapter 7. Each hit is removed or justified with a same-line // danger-scan:allow <reason>, so “clean” is the script exiting 0. Where the compiler can do better — OptionPartial distinguishing opt.get from map.get(k) — prefer the compiler; this exists for portability and for patterns no rule expresses.

    ledger.sh, chain-state.sh, checkpoint.sh — the discharged clause, mechanised

    Chapter 12 covers the reasoning; this is where the three scripts live in the mechanical/judgement split. F7 (above) and F9 answer bound and resolved — a requirement is named by an obligation, and the obligation's artifact exists. Neither answers whether that artifact was ever observed to run green, which is the third clause of what this workflow means by correct, and it had no mechanism at all before schema v12. 

    $ scanner/ledger.sh append --file evidence-ledger.jsonl --change my-change \
    --spec my-spec --ring R3 --obligation "…" --artifact tests/foo.bats \
    --command "bats tests/foo.bats" --exit 0 --baseline $(git rev-parse HEAD)

$ scanner/chain-state.sh --change-dir openspec/changes/my-change \
    --change my-change --baseline $(git rev-parse HEAD)
{"total":9,"bound":9,"resolved":9,"discharged":7,
 "unresolved":[{"spec":"my-spec","requirement":"…","reasons":["undischarged"]}]}

$ scanner/checkpoint.sh report --ledger evidence-ledger.jsonl --change my-change \
    --spec my-spec --baseline $(git rev-parse HEAD) --rings R0,R1,R3,R8 \
    --chain-state-json <(scanner/chain-state.sh …) --format text
  R0: green (bash -n scanner/checkpoint.sh)
  R3: no recorded evidence

    ledger.sh is append-only — there is no update or delete subcommand, on purpose — and every row carries the command that produced it, so a row is re-checkable, not merely trusted. chain-state.sh never re-derives bound/resolved itself; it reads spec-lint.sh's own F7/F9 output and attributes it back to requirements, because a second implementation of reachability is exactly the drift this workflow exists to remove. checkpoint.sh in turn never re-derives ring outcomes — it reads the ledger and reports a ring green only when a matching, zero-exit row exists at the current baseline; a row recording a failed run is reported failed, never green, and a ring with no row at all is no recorded evidence — never silently absent, never silently clean.

    Found inside the tool built to prevent it

    chain-state.sh's first adversarial review found that its own exact-title matcher could find zero rows for a title spec-lint.sh's own (looser) F7 already called bound — and the unmatched case defaulted resolved/discharged to true, never lowered by an empty loop. A title with no evidence examined at all reported as fully discharged, exit 0. The exact defect this trio exists to eliminate, found inside the first implementation of the trio itself — which is the strongest argument in this whole chapter for a fresh-context adversarial pass over an author's own.

    The concept scanner

    Builds the type inventory by parsing sources with Scalameta. Two bugs in its history are worth carrying as lessons.

    Bug 1 · the silent empty scan

    It looked for src/main/scala at the project root. On a multi-module build (adk4s-core/src/…) it found zero concepts and reported success. An empty result that looks like an empty project is worse than a crash. Fix: discover every src/ root in the repo.

    Bug 2 · prose as types

    Regex extraction catalogued consolidates, definitions, prefixing, value, values as sealed types — words appearing near “sealed” in comments — and missed nested declarations entirely. Fix: parse; a comment is not a declaration.

    Today it reports 469 accurate rows on this repository with zero parse failures, qualifies nested declarations (RunnableOps.FallbackSemantic) the way Metals and SemanticDB name them, enumerates sealed-trait variants, links service-trait implementations across files including anonymous ones, and — importantly — counts and reports files it could not parse. A nonzero parse-failure count means an incomplete scan, not a clean one.

    Semantic code intelligence

    The workflow's repeated searches — find references, inspect a symbol, scan for downstream catch-alls — are exactly what text search does worst. On this repository, roughly 31% of git grep hits for a type name were comments or strings, and grep cannot distinguish this project's AgentEvent from a dependency's identically-named one.

    The answer is a headless Metals language server driven from shell scripts, so the recipes are versioned with the schema and work from any agent: 

    $ scanner/metals-start.sh              # per project: free port, JDK check,
                                      # writes .metals/mcp.url for discovery
$ scanner/metals-call.sh resolve AgentEvent
org.adk4s.core.interrupt.AgentEvent
org.llm4s.agent.streaming.AgentEvent          # ← grep would conflate these

$ scanner/impact-scan.sh org.adk4s.core.interrupt.AgentEvent
  reference set: 67 refs in 10 files — semantic (Metals get-usages)
  catch-all match arms near a usage:
    …/EventStreamExample.scala:89   case other =>   (usage at line 72)
    RecipeWorkflow stepWhat it composes
    impact-scan.shstep 0 widening scan compiler-resolved reference set + syntactic catch-all detection, digested
    removal-audit.shstep 12 removal audit --suggest lists removals from the baseline diff; per-symbol verdicts (orphan-candidate = self-references only)
    metals-call.shanywhere bridge: resolve, inspect, get-usages, get-docs, compile-file
    Two rules that keep semantic tools honest

    Freshness. A semantic answer comes from an index, and a stale index is worse than grep — grep's failure mode is noisy, an index's is silent and confident. Trust semantic answers only after a successful compile; during pre-implementation phases (drafting a contract against code that does not exist), the syntactic tools are the honest ones.

    Resolve first. get-usages on an unresolvable name silently degrades to package usages — a flood of line-1 hits that looks like a huge reference set. The recipes resolve names first and guard against that degradation; do the same for ad-hoc calls.

    Every recipe degrades to git grep on its own when no endpoint is running, and says so in its output. Semantic search is an accelerator, never a dependency — which is the same principle as the portability rule, applied to a different axis.

    The artifact graph (prototype)

    The workflow already is a graph — concepts declare actions, specs cite concepts, obligations name requirements, artifacts enforce them — but the gate checks verify those edges pairwise. The prototype makes the graph explicit so it can be queried transitively: 

    $ scanner/openspec-graph.py impact MemoryAwareRunner
  syncs defined: RecallToContext, WriteEpisode
  add-cross-run-memory-example/cross-run-memory-example
    ✓ R1: File-backed memory persists episodes across process boundaries
        3 obligation(s) -> FileBackedAgentMemorySpec, spec §"Non-goals"
    …
  reach: 1 spec, 8 requirements, 19 obligations, 8 enforcing artifacts

$ scanner/openspec-graph.py obligations
  verdict: PASS — every requirement reaches an artifact

    Its first run found the schema gap that became the Source-format mandate in chapter 5. It is Python, so it stays advisory — the same reachability check now also exists as F7 in the portable linter, which is the version that gates.

    Mechanical vs judgement — the honest split

    Fully mechanicalJudgement, tool-assistedHuman only
    Source format (F6)
    Requirement reachability (F7)
    Registry symbol drift
    Fold-field declarations
    Exhaustiveness (Ring 0)
    Mutation score
    Concept & dependency deltas
    Discharged evidence (ledger + chain-state)     		Observability of a Then
    Testability with this stack
    Whether a property is vacuous
    Adversarial review verdicts
    Equivalent-mutant judgements
    Ring selection     		Is the requirement the right one?
    Is this risk acceptable?
    Is the design the right shape?
    MUST-CONFIRM data
    Accepting PARTIAL verdicts

    The third column is chapter 1's adequacy row, and no tool in this chapter touches it. The workflow's goal is not to eliminate that column — it is to shrink the first two so ruthlessly that human attention is spent entirely on the third.

    A column this table does not have

    Every tool above is opt-in. The CONTEXT block cures N/A-by-assumption only if spec-lint.sh runs at all; the drift check reports a stale skill only to whoever invoked it. Mechanising a check answers what happens when it runs and leaves whether it runs untouched — which is a separate mechanism, and chapter 11.

    Setup, briefly

    # gate checks — nothing to install
$ openspec/schemas/verified-scala3/scanner/spec-lint.sh openspec/changes/<change>
$ openspec/schemas/verified-scala3/scanner/registry-check.sh .

# scanner (needs scala-cli)
$ scanner/scan.sh . --output openspec/concept-inventory.md    # create
$ scanner/scan.sh . --output /tmp/scan.md                     # verify: diff, never overwrite

# semantic recipes (needs coursier + JDK 17+), once per project
$ cs install metals-mcp && scanner/metals-start.sh

# agent skills into .claude/ .pi/ .devin/
$ scanner/install-skills.sh

    Wire registry-check.sh and spec-lint.sh into CI — ready-made templates for GitHub Actions, GitLab and Azure are in the schema's ci/ directory.
