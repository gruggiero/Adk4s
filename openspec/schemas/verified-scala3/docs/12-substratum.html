    The correctness substratum

    Chapter 5 gave you two clauses of correctness: a requirement is bound to an obligation, and the obligation's artifact resolves to something that exists. Neither clause asks whether that artifact was ever actually run. This chapter is the third clause, and the tooling that makes it a fact rather than a memory.

    The gap the first eleven chapters left

    Re-read chapter 5 carefully and the gap is exactly where you'd expect it, because it is the same gap every earlier chapter found somewhere else. F7 answers is this requirement named by an obligation. F9 answers does the obligation's artifact exist. Once both are true, the proof-obligations table reports a row complete — and stays reporting it complete for as long as the artifact exists, whether or not anyone has run it since the code around it last changed.

    The fault dataset was the schema's own changelog

    This chapter's motivating evidence did not come from a new incident. It came from re-reading the schema's own version history (now in CHANGELOG.md, sibling of schema.yaml) as what it actually is — a record of defects this workflow has already found in itself — and noticing the same shape recurring: a check reported PASS on evidence it never obtained. The altitude rule read N/A from memory instead of the filesystem (chapter 9). A version field sat three schema versions stale because nothing compared it (chapter 9, again). Chapter 11 found gate.sh could say nothing at all and be indistinguishable from working correctly, until it started tracing its own silent runs. Three different rings, three different artifacts, one recurring bug: a claim that outran its evidence. That pattern, seen three times, is a substratum problem — it needs one fix that applies everywhere, not a fourth patch to a fourth symptom.

    Three clauses, not two

    So the definition of correct gets a third clause, and the workflow states it as a standing rule rather than a per-check property — something true no matter the ring, the step, or the artifact:

    Rule · the operative sentence, verbatim, everywhere

    A requirement is correct when it is

    1. bound — named by a proof obligation (F7);
    2. resolved — the obligation's artifact exists (F9);
    3. discharged — the artifact was observed to run green, in this session, with a recorded command.

    And the sentence schema v12+ injects into every artifact instruction and every apply-phase turn, unabbreviated: “NEVER LET A CLAIM OUTRUN ITS EVIDENCE.” — “N/A” / “passes” / “already handled” are CLAIMS, not verdicts.

    Clause 3 is the one no earlier chapter's tooling could answer, because answering it needs something none of them kept: a durable record of which commands were actually run, against which baseline, with what result. That record is the evidence ledger, and it is the only genuinely new state this chapter introduces — everything else is either derived from it or from the F7/F9 machinery you already have.

    The evidence ledger

    scanner/ledger.sh is deliberately the simplest thing that could make clause 3 mechanical: an append-only log, one JSON object per line, of commands that were actually run. It has three subcommands: append (legacy, agent-supplied exit), run (capture, script-observed exit), and verify (replay, re-executes and compares). 

    # capture mode — the script executes the command and observes the exit itself
$ scanner/ledger.sh run --file evidence-ledger.jsonl \
    --change my-change --spec my-spec --ring R3 \
    --obligation "the parser round-trips" --artifact tests/ParserSpec.scala \
    --baseline $(git rev-parse HEAD) -- sbt parserSuite/test
ledger: run recorded exit=0 wallTime=1740ms

$ scanner/ledger.sh read --file evidence-ledger.jsonl \
    --change my-change --baseline $(git rev-parse HEAD)
{"v":1,"ts":"2026-08-12T12:00:00Z","change":"my-change","spec":"my-spec",
 "ring":"R3","obligation":"the parser round-trips",
 "artifact":"tests/ParserSpec.scala","command":"sbt parserSuite/test",
 "exit":0,"baseline":"a1b2c3d…",
 "sha256":"9f86d081…","digest":"e3b0c442…","wallTime":1740}

    Four design choices carry all the weight, and each closes a specific way a claim was found to outrun its evidence during this exact chapter's own construction:

    Append-only, structurally

    There is no update or delete subcommand — not a permission you could misuse, a verb that does not exist. A recorded run is evidence; evidence that can be edited after the fact is testimony. The one thing append mode does not prevent is in-process forgery — nothing stops a caller appending a row for a command it never ran, with any exit code it chooses. Capture mode (run) closes that gap: the script executes the command itself, records its own observed $?, and rejects --exit as an argument. Recording the command makes a row re-checkable (verify), which moves forgery from the default path to a deliberate act. That is the honestly-stated limit, not a claim of more.

    Baseline-scoped, exactly

    Every row carries the commit SHA it was run against. A row is evidence for that baseline and no other — a green run before an edit does not discharge the obligation after it. Reading without a baseline (which the reader permits, for callers who genuinely want everything) is different from a caller who discharges something from a read: every caller that does, in this schema, supplies the baseline itself, without exception. The --forgive-unchanged flag extends this: a row remains discharged until its artifact actually changes (git diff --quiet <baseline> HEAD -- <artifact>), so a ring that ran green three specs ago is not falsely indicted just because HEAD advanced.

    Content-hashed, at record time

    A run row carries the artifact's SHA-256 (sha256), the stdout/stderr digest (digest), and the wall-clock duration (wallTime). Without the content hash, a row says "the artifact ran green" but cannot verify that the artifact present now is the one that ran. On replay divergence, the digest tells whether the output changed; the wall time tells whether the environment degraded. Legacy append rows lack these fields, and that is valid — both shapes read cleanly from the same file.

    Replayable, not merely trusted

    ledger.sh verify re-executes each row's command, compares the observed exit to the recorded exit, and reports per-row replay matches, replay diverges, or manual/unreplayable. A diverging row exits non-zero and names the row; a manual/R8 row is explicitly named, never silently skipped. "A row records the command and its exit, so it is re-checkable by re-running it" — verify is the command that actually runs it.

    Two bugs the ledger shipped with, found by Ring 8, fixed before merge

    Trailing-newline corruption. Appending onto a file whose last byte was not already a newline concatenated the new record onto the previous row — silently, permanently. The reader explicitly supports a file with no trailing newline (a legitimate shape), so the writer now owns the record separator instead of assuming the file's tail is clean.

    An unreadable ledger read as a clean zero. A chmod 000 ledger produced exit 0 and zero rows — absence of evidence presented as evidence of absence, the exact sentence the operative rule forbids, found inside the very first script written to enforce it. Fixed with explicit readability checks that fail to undetermined, never to a silent, confident zero.

    Chain state — never reimplemented

    scanner/chain-state.sh answers the question a checkpoint actually needs: for this change, at this baseline, how many requirements are bound, resolved, and discharged — and which ones are not, named. 

    $ scanner/chain-state.sh --change-dir openspec/changes/my-change \
    --change my-change --baseline $(git rev-parse HEAD)
{"total":9,"bound":9,"resolved":9,"discharged":7,
 "unresolved":[
   {"spec":"my-spec","requirement":"the parser round-trips","reasons":["undischarged"]},
   {"spec":"my-spec","requirement":"the retry policy holds","reasons":["failed"]}
 ]}

    Follow chapter 9's own rule here: bound and resolved are never recomputed. chain-state.sh reads spec-lint.sh's own F7 and F9 output and attributes each hit back to a requirement title — a second implementation of reachability is the exact drift defect chapter 9 spent a whole section on. Discharged is the one genuinely new computation: every mapped obligation must have at least one matching, same-baseline ledger row with exit: 0.

    Two reason-codes distinguish why a requirement is unresolved: undischarged means no matching ledger row exists at all; failed means a row exists but records a non-zero exit — the ring ran and broke, which is different from "never ran" and must not be conflated. A recorded red run is negative evidence, visible as such, not silently folded into the same bucket as absence.

    Found inside the tool built to prevent it

    The first version's exact-title matcher could find zero rows for a title spec-lint.sh's own — looser — F7 already called bound (it accepts ordinals and case-insensitive substrings; this script's matcher did not). The unmatched case left is_resolved/is_discharged at their default of true, never lowered by an empty loop. A title with zero evidence examined reported as fully discharged, exit 0 — the precise failure this whole chapter exists to eliminate, reproduced inside the first script written to prevent it.

    The fix added a fourth classification, unattributable, checked before a title can ever be counted resolved or discharged: a bound title this script cannot itself attribute evidence to is reported as exactly that, never silently folded into “fine”. In graph mode (when python3 is available) the graph resolves titles uniformly, so unattributable never appears; it remains the safety net for bash degraded mode. Two more bugs in the same family — substring matches (grep -qF without -x) letting one title's verdict bleed onto another whose name happened to be a prefix, and onto an unrelated line number 260 lines away — were fixed by anchoring every lookup to the whole line, not a fragment of it.

    The substratum review — eight more, same shape

    A fresh-context review of the substratum itself (docs/openPoints/verified-scala3-substratum-review.md, 2026-08-12) found eight defects (D1–D8), all the same shape: a claim that outran its evidence. The two critical ones:

    • D1 — a failed run discharged the obligation. chain-state.sh matched on spec+obligation and never checked .exit. A row recording "exit": 1 discharged the obligation — directly contradicting the schema's own definition ("observed to run green"). Every discharged fixture used --exit 0; the "recorded red run" case was untested. Fixed by gating discharge on exit == 0 and adding the failed reason-code so a red run is visible as negative evidence.
    • D2 — HEAD advanced, every prior spec went stale. The gate computed chain state at git rev-parse HEAD for every active change. After spec N committed, HEAD advanced and every prior spec's ledger rows read stale — the gate reported earlier specs undischarged forever unless every ring was re-run after every commit. Fixed with per-spec baselines (read from implementation-progress.md) and --forgive-unchanged (a row stays discharged until its artifact actually changes).

    The remaining six (D3–D8) address the ledger's trust model (capture mode, replay, content hashes), parser divergence (single fact extractor, JSON output), and hygiene (dangling references, dead code, heartbeat pollution). Each was found by the workflow's own Ring 8 mechanism — the substratum reviewing itself, which is the strongest argument for fresh-context adversarial review of an author's own.

    The checkpoint, generated

    Chapter 8 already told you what changed here; this is the mechanism behind it. scanner/checkpoint.sh report reads the ledger and a chain-state report and renders the same Rings: line the checkpoint format has always had — except now every green citation traces to a row, and a ring with none is no recorded evidence, never a quiet green by omission. 

    $ scanner/checkpoint.sh report --ledger evidence-ledger.jsonl \
    --change my-change --spec my-spec --baseline $(git rev-parse HEAD) \
    --rings R0,R1,R3,R8 --chain-state-json <(scanner/chain-state.sh …)
  R0: green (bash -n scanner/checkpoint.sh)
  R1: green (shellcheck scanner/checkpoint.sh)
  R3: FAILED (bats tests/checkpoint-from-ledger.bats, exit 1)
  R8: no recorded evidence
    A row is evidence of what happened, not of success

    The first version reported any matching row as green — it copied the row's own exit code into its output object two lines later without ever reading it first. A ring that had regressed after an earlier green run was still reported green, citing the now-failing command. Fixed by gating status on exit == 0; a non-zero row now reports failed, visibly distinct from no recorded evidence — a human should be able to tell “never ran” from “ran and broke” at a glance, and before this fix, the checkpoint could not.

    checkpoint.sh regenerate-tasks closes the other half of the loop chapter 2 named: a spec counts as complete when its tracker entry's Commit field holds a real hash, and tasks.md's checkboxes are rewritten from that — never hand-toggled, never able to independently drift from the tracker again.

    And ledger.sh verify closes the loop the ledger itself opened: a row records the command and its exit, so it is re-checkable by re-running it. Before verify, that sentence was a promise — the command was stored, but nothing ran it. Now verify re-executes every replayable row, compares exits, and reports replay matches or replay diverges per row, exiting non-zero on any divergence. Manual/R8 rows are named manual/unreplayable, never silently skipped. A ledger that passes verify is evidence that the recorded exits are still the exits you would get — which is the strongest statement a re-checkable record can make.

    The hooks that block

    Chapter 11 told this part of the story in full, including the two bugs that would have shipped a silently inert — or silently unbounded — block if a fresh-context review had not caught them first. The short version, for continuity: once chain state can answer discharged mechanically, refusing a turn that claims completion while chain state disagrees becomes possible for the first time, and it is deliberately the last thing this chapter's tooling built — after the ledger, after chain state, after the generated checkpoint had all run cleanly on their own.

    Schema v13 then added the pre-execution tool_call gate, which made enforcement universal. The completion gate is a 2/3-harness backstop: it works on Claude Code and Devin, but pi has no blocking completion event in its extension API. The pre-execution tool_call handler — wired into all three adapter configs at v13 — is the tier that exists everywhere. On pi it is the only enforcement surface. The completion gate catches an agent that claims "spec complete" while its evidence says otherwise; the pre-execution gate catches an agent that is about to make an edit while the same evidence is unresolved — a different moment, on a different event, and the one that is not limited by which harness you happen to be running under.

    Why this had to be last, not first

    A blocking gate is only as trustworthy as the evidence it blocks on. Had the completion gate shipped before the ledger's trailing-newline bug or chain-state's title-matching fix (unattributable in bash mode, eliminated by the graph in graph mode), it would have been refusing turns — or worse, silently permitting them — on a chain-state computation that was itself capable of reporting a clean zero on no evidence at all. Sequencing the substratum's own construction this way is the same lesson as chapter 11's Tier B before Tier A, applied one level deeper: promote enforcement onto evidence you have already verified is honest, never onto evidence you are still debugging.

    Where it lives in the ladder

    Chapter 9 split every check into fully mechanical, judgement, and human only. Chapter 11 gave enforcement five rungs, prose to CI. Clause 3 moved across both in one release: it went from not represented at all to fully mechanical (chapter 9's table — ledger and chain-state need no human judgement to compute) and reached rung 4 of the enforcement ladder the same day it shipped, because the hook and the mechanism it enforces were designed together rather than bolted on afterward.

    Analogy · a substratum, not a rule

    Every earlier chapter's mechanism answers a question about one artifact — does this spec obey F7, does this diff pass Ring 1. The operative rule is different in kind: it is not one more check alongside the others, it is the standing condition all of them are supposed to satisfy, restated wherever an agent is about to render a verdict. That is why it is injected into every artifact instruction rather than living in one spec-lint check (chapter 9's own CONTEXT-block lesson, applied to the rule itself, not just to one rule's applicability facts).

    Check yourself

    Before moving on, you should be able to say

    • The three clauses of correctness, and which one had no mechanism before this chapter.
    • Why the evidence ledger is append-only structurally, not by convention — and what run mode adds that append cannot.
    • Why chain-state.sh never recomputes bound/resolved itself, and what unattributable is for (bash degraded mode; in graph mode the graph resolves titles uniformly).
    • The difference between undischarged (no row) and failed (row with non-zero exit) — and why conflating them is the same bug as conflating "never ran" with "ran and broke".
    • What ledger.sh verify adds: a row was re-checkable in principle; verify makes it re-checked in practice.
    • Why the completion gate shipped last, and what would have gone wrong had it shipped first.
    • The difference between the completion gate (2/3-harness backstop, schema v12) and the pre-execution tool_call gate (universal, schema v13) — and which one exists on pi.

    If you can only take one idea from this whole tutorial, it is the sentence this chapter states as a rule rather than derives from one: never let a claim outrun its evidence — including this workflow's own claims about itself, which is exactly where the bugs above were found, twice: first inside the substratum's own construction, then again in the fresh-context review that found eight more.
