    The verification rings

    Ten mechanisms, each catching a class of defect the others structurally cannot. This chapter is what each one actually detects, what it costs, how it fails, and why the execution order is what it is.

    The organising principle

    Rings are numbered by fundamentality — how close to the metal the check is — and executed in an order chosen by economics. Those differ, and the difference is deliberate: 

    numbering    0 compile · 1 lint · 2 architecture · 3 tests · 4 compat
             5 mutation · 6 formal · 7 model · 8 adversarial · 9 telemetry

execution    0 → 1 → 2 → 3 → 4 → 8 → 5 → 6/7 → 9
                                  ↑
                    cheap, changes code, adds tests — so it must
                    precede mutation, which measures the final suite

    Each ring answers a question no earlier ring can. Click through them:

    Why this particular order

    Three constraints determine it, and once you see them the sequence is forced:

    1. Prerequisite. Ring 3 cannot run before Ring 0 — the tests must compile. Ring 5 mutates code that must already pass its tests, or every mutant “survives” meaninglessly.
    2. Cost gradient. Cheap, fast, deterministic checks first; a defect that Ring 0 can catch should never reach Ring 5.
    3. Stability. A ring that changes code must precede rings whose results describe the final code. This is the whole argument for 8 before 5.
    Why it is designed this way · the ordering bug that existed

    Earlier versions ran mutation → formal → adversarial, in numeric order. The result: adversarial review would add two tests, which is its normal outcome — and the mutation score in the checkpoint now described a suite that no longer existed. Either you re-ran the slowest ring, or you filed a number you knew was stale. Moving Ring 8 earlier fixed both, and cost nothing: reading is cheap.

    Empirical support, from the schema reviewing itself

    The clearest evidence for the fresh-context mandate came from building the correctness-substratum tooling (chapter 12) using this exact workflow. On its first spec, the author's own Ring 8 pass reported 1 FAIL and the spec complete. A fresh-context reviewer, given only the spec, the approved contract, and the diff — not the conversation that produced the code — returned 11 findings against the same commit, several of them the precise “a check reports a verdict on evidence it never obtained” failure this whole workflow exists to catch. That result was enough to adopt a standing rule — fresh context only, no author self-review, from then on — so the remaining five specs have no author-pass number to compare against. What they do have is a fresh-context pass that kept finding real, reproducible defects anyway (3 to 9 per spec) in code that had already passed every ring, including its own tests. The rule was not adopted on one data point and left untested; it kept earning its cost on every spec that came after.

    What each ring is blind to

    This table is the most useful thing in the chapter. Defence in depth only works if the layers have different holes:

    RingStructurally cannot see
    0 compileany wrong value; any wrong logic that type-checks
    1 lintwhether the code does the right thing; only shapes
    2 architecturebehaviour entirely; a perfectly layered wrong answer passes
    3 testsrequirements nobody wrote a test for; unsampled inputs; unexplored interleavings
    4 compatibilitywhether the new behaviour is correct — only that the old shape survives
    5 mutationmissing requirements — it measures the suite against the code, never against the spec
    6 formalanything effectful, and whether the contract itself is the right one
    7 model checkingthe gap between the model and the actual implementation
    8 adversarial reviewwhat a human reader misses: subtle arithmetic, rare interleavings, scale
    9 telemetryanything that has not happened in production yet

    Read row 5 twice. Mutation testing cannot detect a missing requirement — it perturbs code that exists and asks if tests notice. If the spec forgot a rule, there is no code to mutate, no test to fail, and a 95% mutation score. This is exactly why the workflow anchors everything to a reviewed spec: no amount of test-quality measurement can find what nobody specified.

    Two hypotheses behind mutation testing

    Prior art

    Mutation testing rests on two assumptions worth knowing, because they tell you when it works. The competent programmer hypothesis: programs are written by competent people, so real faults are usually small deviations from correct code — which is what mutation operators simulate. The coupling effect: tests that detect simple faults also tend to detect complex faults built from them.

    Empirical work supports both well enough that mutation score correlates with real fault detection better than coverage does — which is the practical claim that matters. UCL CREST mutation testing theory.

    The honest caveat: equivalent mutants. Some mutations produce semantically identical programs, so no test can kill them; deciding equivalence is undecidable in general. That is why the workflow requires each survivor be killed, marked equivalent with an explanation, or excluded with rationale — the judgement is recorded, not hidden in a threshold.

    Choosing rings for a change

    The proposal declares which rings apply. Some heuristics that hold up:

    If the change…Then…
    touches serialization, persisted events, or wire formatsRing 4 is required, no judgement call
    contains pure computation with real semantics (evaluators, arithmetic, desugaring)Ring 6 is worth its cost; this is where provers shine
    involves ordering, retries, idempotency or replayRing 7 if tooling exists — otherwise an explicit manual obligation, never silence
    is a pure internal refactorRings 0,1,2,3,8 with behaviour-preservation tests; minimal typed contract
    changes an LLM- or caller-facing surfaceRing 3 must assert what the consumer observes (parameter schema, not just presence)
    is docs-only or formatting-onlyRings 0,1 — and a stated Ring 3 waiver with rationale
    The most common mistake in ring selection

    Skipping Ring 4 on a change that “only adds a field”. Adding a field to a persisted event is a compatibility change: old readers meet an unknown field, new readers meet its absence in old data. Both behaviours must be specified. This is the single most common source of “worked in dev, corrupted in prod”.
