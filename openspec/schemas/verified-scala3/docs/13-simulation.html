    Chapter 13 · capstone

    The whole workflow, simulated end to end

    This chapter runs one fake, three-spec change — add-shipment-quoting — through the entire verified-scala3 machine: planning artifacts, the per-spec apply loop (Steps 0–13), hooks firing on every turn, the evidence ledger filling row by row, the completion gate refusing a premature claim, and the final archive. Part A is the static reference (phases, rings, hooks, persisted state). Part B is the stepper. Everything shown in the state panels is cumulative — what you see at step n is exactly what would exist on disk at that moment.

    Simulated change: add-shipment-quoting · 3 specs · detected stack: sbt + munit/ScalaCheck + Stryker4s; telemetry stack absent · sessions: s-work (implementing) and s-review (fresh-context reviewer)

    A1 · The lifecycle at a glance

    Two phases surround one loop. Planning produces the change's artifacts in DAG order; the apply loop then executes one spec at a time through Steps 0–13, with a mandatory human stop after each spec; archive folds the delta specs into openspec/specs/ and the change into openspec/changes/archive/.

    A4 · Hooks — what fires when

    The scripts fix what happens when checks run; hooks fix whether they run. All logic lives in hooks/gate.sh; harness adapters only decide when to ask and where to put the answer.

    Escape hatch: VERIFIED_SCALA3_HOOKS=off. Heartbeat: every invocation — even silent ones — writes --check-installed state under the repo's git-dir (resolved via git rev-parse --absolute-git-dir, so worktrees work). If openspec/ is absent the hook emits nothing at all.

    B · The simulation

    Step through add-shipment-quoting (30 steps; arrow keys work). Left pane: what the agent, hooks, and human do. Right pane: the persisted state at this point — files (tab 1), the evidence ledger (2), per-requirement chain state bound / resolved / discharged (3), and the hook log (4). Freshly-changed rows are highlighted in blue.

    Chain semantics — bound: ≥1 proof obligation names the requirement (spec-lint F7; satisfied once specs pass lint) · resolved: obligation artifacts resolve to tracked files (F9; deliberately not run until Step 12 — an artifact token is a commitment, not a fact, before implementation exists) · discharged: a green run recorded in the ledger at this spec's baseline. Baselines: b0=a1b2c30 (start of spec 1), b1=9f04d1e, b2=77c21aa — each spec's baseline is the previous spec's checkpoint commit.

    What changed in this step

      How to read the verdicts

      • The red→green polarity flips (steps 11, 19) are the evidence the oracle has teeth: a test that never fails when the implementation is absent proves nothing.
      • The tool-call blocks (steps 11, 16) and the completion refusal (step 21) are the moments the harness actively stops the agent: the oracle-ordering lock, the human-grant lock, and the completion gate's single bounded refusal. Everything else is context, not coercion.
      • The resolved column stays “deferred” until Step 12 — artifact tokens are a commitment at spec time and only become facts when --artifacts (F9) runs against the now-existing files.
      • Ring 8 rows carry session: s-review — the checkpoint compares it against the implementing session s-work to enforce the fresh-context mandate mechanically.
      • Every ledger row stores its command and baseline, so "discharged" is re-checkable evidence, not testimony.
