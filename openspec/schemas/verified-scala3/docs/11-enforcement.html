    Chapter 11 · Enforcement

    Making it stick

    Every check in the previous ten chapters is opt-in. An agent that does not run the script never sees the fact that would have corrected it. This chapter is about the difference between a rule that is written down and a rule that is enforced — and about the one mechanism that closes the gap without making the workflow unportable.

    The failure that survives everything so far

    Chapter 9 told the story of a review that recorded the altitude rule as N/A on a repository holding thirty concept files. The fix was a CONTEXT block: spec-lint.sh now prints the applicability facts unconditionally, so N/A becomes something a machine reports rather than something a reviewer concludes.

    Read that fix carefully and you will find a hole in it.

    The residual gap

    The CONTEXT block only helps if the script runs. An agent that skips spec-lint.sh — because it is confident, because the change looks small, because its instructions were three versions stale — never sees the block at all. Every mechanism in chapters 3 through 10 has this shape. The scripts fix what happens when they run. Nothing so far fixes whether they run.

    That is not a bug in any particular check. It is a property of the whole system: verified-scala3, as described up to here, is a documentary workflow. It tells an agent what to do and trusts the report that comes back.

    The enforcement ladder

    There is a ladder here, and it is worth naming because it mirrors the mechanism ladder for proof obligations from chapter 5. Each rung removes a different opportunity for the rule to be quietly skipped:

    The same move, one level up

    F10 took a question the reviewer was answering by judgement — does this spec cite its concepts? — and made it a fact. A hook takes a question the agent was answering by choice — should I run the linter? — and removes the choice. Both are the same operation: find the step that depends on someone remembering, and delete the remembering.

    What a hook actually is

    A hook is a command the agent harness runs at a named lifecycle event, passing it a JSON description of what is happening, and reading back a decision. The remarkable thing — and this is what makes the whole approach viable for a workflow that must run under several different agents — is how strongly the contract has converged: 

    # the harness invokes:  gate.sh < event.json
{ "hook_event_name": "SessionStart",
  "session_id": "…", "cwd": "/home/you/project" }

# the script answers, on stdout:
{ "hookSpecificOutput": { "additionalContext": "…facts for the model…" } }

# or refuses the action outright:
{ "decision": "block", "reason": "spec-lint: 3 FAIL" }     # or: exit 2
    Read that comment literally — exit 1 is not on the list

    Claude Code treats exit 1 as a non-blocking error: the action proceeds and the harness moves on. Only exit 2, or the decision:block JSON on a normal exit-0 response, actually refuses anything — and on exit 2 specifically, the reason is read from stderr, not the stdout shown above. A hook that gets this wrong does not fail loudly; it fails by quietly doing nothing, which is the one failure mode this whole tutorial is about. This is not a hypothetical warning — see the box further down this chapter for where it happened for real.

    Claude Code, Codex CLI and Devin CLI arrived at that contract independently. A script written for one runs unmodified under the other two; only the config file that points at it differs.

    Are hooks portable across agents?

    Partly — and the part that is not portable turns out not to matter. Here is the landscape, checked against primary sources rather than recollection:

    AgentConfigStyleCan block?
    Claude Codesettings.json (also HTTP)shell, JSON stdin/stdoutyes — exit 2 / permissionDecision
    Devin CLI.devin/hooks.v1.jsonshell, JSON stdin/stdoutyes — exit 2 / decision:block
    Codex CLI~/.codex/hooks.jsonshell, JSON stdin/stdoutyes
    Cursor~/.cursor/hooks.jsonshellyes
    pi.pi/extensions/*.tsTypeScript, in-processyes — return { block: true }
    OpenCodeTS plugin moduleTypeScript, in-processyes

    Two families, then: a shell family that shares one contract, and an in-process TypeScript family that is richer and typed. And the five events this workflow needs — SessionStart, UserPromptSubmit, PreToolUse, PostToolUse, Stop — exist in every one of them, under different names.

    Rule · the transferable unit is the script, not the config

    Put all logic in a shell script with a plain CLI. Keep every per-agent adapter trivial enough to read in one screen: it decides when to ask and where to put the answer, nothing else. The TypeScript family can spawn the same script, so one implementation serves six harnesses. Any logic that leaks into an adapter is logic you now maintain six times — and five of those copies will drift.

    Empirical support, from an unrelated tool

    The session-observability tool orca ships thirteen agent adapters — claude, devin, codex, cursor, copilot, gemini, grok, kimi, droid and more. They are byte-identical except for one URL path. Someone else, solving a different problem, converged on the same architecture: one payload contract, thirteen trivial bindings.

    The prototype: gate.sh

    The workflow's hook entry point is openspec/schemas/verified-scala3/hooks/gate.sh. Two design decisions in it are worth stealing whatever you are building.

    One implementation of the facts

    gate.sh does not compute the applicability facts. It shells out to spec-lint.sh --context-only, which was added for exactly this purpose: 

    context="$(bash "$SCANNER/spec-lint.sh" --context-only "$REPO")"

    Recomputing them inside the hook would have been three lines shorter and would have created a second implementation that could disagree with the one the lint reports. That is the drift defect from chapter 9 — the version field nobody read — rebuilt deliberately, by hand. The same reasoning governs workflow position, which is derived from the artifact DAG in schema.yaml rather than from a list copied into the script.

    Silence where it does not apply

    [ -d "$REPO/openspec" ] || exit 0

    A hook installed globally runs in every repository you open. If it emits anything at all in projects that do not use this workflow, it is noise; noise gets disabled; and a disabled hook enforces nothing. The cheapest way to keep an enforcement mechanism alive is to make it invisible wherever it is irrelevant.

    Start non-blocking

    The tempting first hook is the powerful one: block the commit until spec-lint passes. Resist it for one release.

    Tier B · inject context (start here)

    At session start, read the applicability facts and the workflow position off disk and hand them to the model. It cannot misjudge whether the registry exists, because the answer arrives before it can guess. Never blocks; always exits 0. Worst case if it breaks: the agent gets no extra context, exactly as before.

    Tier A · gate the action (earn it)

    Lint on every spec.md write; registry-check before commit. Strictly better when it works. Worst case if it breaks: a failing check the agent cannot satisfy and cannot bypass, and a workflow that now prevents work rather than guiding it.

    The asymmetry in those failure modes is the whole argument. Ship Tier B, live with it, and promote to Tier A on evidence rather than on enthusiasm. Whatever you ship, give it an escape hatch — VERIFIED_SCALA3_HOOKS=off — because the person who needs to bypass your gate at 2am should not have to edit JSON to do it.

    What actually shipped, and what nearly went wrong

    This is not a hypothetical ladder. gate.sh ran Tier B only through five specs of the correctness-substratum work (chapter 12) before Tier A was proposed — zero session-strand incidents in daily use is what “on evidence” means in practice, not a fixed calendar interval. Tier A itself split the same way the two-column box above predicts: post-edit (findings only, still cannot block) shipped first; the one genuinely blocking event in this whole schema — completion, refusing a turn that claims a checkpoint while the evidence ledger (chapter 12) shows unresolved requirements — shipped last, and only after post-edit had itself run cleanly.

    The near miss, found by the fresh-context review before it shipped

    The first implementation of the completion gate was silently inert on its most common path. It signalled a refusal with a raw script exit code (1), and Claude Code's own hook contract treats exit 1 as a non-blocking error — the turn proceeds, the refusal never happens, and nothing says so. A second bug was worse in the other direction: the bounded-refusal guarantee lived entirely in a state-file marker, and when that state could not be created (no .git yet is a real, ordinary condition), refusal had no bound at all — every attempt blocked, forever. That is the exact “blocking hook that misfires and cannot be escaped” failure this chapter warned about above, found inside the first attempt to build the hook the warning was about.

    Both were caught by Ring 8's fresh-context review, before either line reached a live session — reproduced with real commands against the real script, the same discipline chapter 7 describes. The fix for the second bug is the general lesson: a blocking decision may only be made when the mechanism that bounds it is actually available; when it is not, the event fails open, not closed. An enforcement mechanism that cannot prove its own escape hatch works has no business blocking anything.

    Verifying a hook fires

    This deserves its own section because the obvious test is not sufficient. A hook has three independent ways to fail, and running the script by hand rules out only the first.

    LevelTestRules out
    1run gate.sh yourselfa broken script
    2set VERIFIED_SCALA3_HOOKS_TRACE, start a session, read the logconfig the harness never picked up
    3ask the model something only the injected block knowsthe harness ran it and dropped the output
    Rule · log the silent runs too

    gate.sh writes a trace line on every invocation, including the ones that deliberately emit nothing. Without that, “fired and correctly stayed silent” and “never fired at all” produce identical evidence — an empty log — and you would spend an afternoon debugging a hook that was working perfectly. 

    2026-08-07T19:07:31Z  event=session-start  repo=/…/adk4s   emit: 1396 chars
2026-08-07T19:07:31Z  event=session-start  repo=/…/plain   skip: no openspec/ here
2026-08-07T19:07:31Z  event=session-start  repo=/…/adk4s   skip: VERIFIED_SCALA3_HOOKS=off

    Level 3 is the one that actually matters, and it has a pleasing symmetry with why the hook exists at all. The hook is there to stop an agent answering a repository question from memory. So the test is whether it can now answer one without looking:

    “How many concept files does the CONTEXT block report, and does the altitude rule apply?” — asked before the agent runs any tool. A correct answer with no tool call means the injection landed. If it has to go and look, the context was dropped somewhere between the harness and the model.

    Where hooks are the wrong tool

    The failure mode of learning about hooks is hooking everything. Three places where they are actively a bad idea:

    • The expensive rings. Rings 3, 5 and 6 take minutes. A hook that runs the test suite on every edit destroys the loop it was meant to protect. These belong to the apply loop and to CI, unchanged.
    • Judgement. Altitude compliance, observability, testability. A hook can force the question to be asked; it can never answer it. Same boundary as chapter 9 — do not let a hook's green exit code imply a judgement was made.
    • The human gates. A Stop hook can refuse to end a turn until the typed-contract review is recorded. But that fights the human rather than the agent, and a blocking Stop hook that misfires is genuinely difficult to escape.
    A narrower use of Stop is not this mistake

    Chapter 12's completion gate also uses Stop, and it is worth being precise about why that is a different thing than the bullet above. It never waits on a human decision — a typed-contract review, an approval that has not arrived — it refuses only when the agent's own turn asserts a claim (“spec complete”) its own evidence contradicts. That is fighting the agent's tendency to proceed plausibly (chapter 8), not the human's pace, and the bounded-refusal design above exists specifically so it cannot degrade into the failure this bullet warns about. Gating on a human decision with a blocking hook is still the mistake; refusing an unsubstantiated claim, once and escapably, is not the same mistake wearing a different label — but it is exactly the kind of subsystem worth building last, after everything non-blocking has proven itself, and worth reviewing hardest.

    The risks, stated plainly

    A hook is not a skill

    A skill is inert text an agent may choose to read. A hook is a shell command the harness executes, on every session, with your full permissions. When a workflow is vendored into many repositories, a hook config that ships with it runs on every collaborator's machine that installs it. That is why install-hooks.sh is a separate command from install-skills.sh, defaults to a dry run, and prints exactly what it would write. Installing enforcement should be a decision, not a side effect.

    Two smaller ones worth designing against. Deadlock: a blocking gate that fails for an unrelated reason leaves the agent with no legal move — hence fast, high-precision checks only, F-level never W-level, and always an escape variable. Duplicate enforcement: once a check runs from both the skill and the hook, the report should record which produced the output, or you have reinvented drift in a new location.

    The through-line

    Every chapter of this tutorial has made the same move in a different place. Chapter 1 refused to accept a green suite as evidence. Chapter 5 refused to accept an obligation without a named mechanism. Chapter 9 refused to accept N/A without a machine-attested fact. This chapter refuses to accept “the instruction says to run it” as evidence that it ran.

    The pattern generalises past this workflow, and it is worth carrying: wherever a process depends on someone remembering to do something, that dependency is the defect. Not the person, not the agent — the dependency. Find it and delete it, one rung at a time, and be honest in an artifact about the rungs you did not climb.

    Check yourself

    You should now be able to:

    • Explain the difference between a documentary rule and an enforced one, and place any check on the five-rung ladder.
    • Say why the hook script transfers across agents while the hook config does not — and design so only the script matters.
    • Justify shipping context injection before blocking gates, in terms of the two failure modes.
    • Verify a hook at all three levels, and explain why an empty trace log would be ambiguous if silent runs were not logged.
    • Name three things that should not be hooks, and why.

    If you can only take one idea: find the step that depends on someone remembering, and delete the remembering.
