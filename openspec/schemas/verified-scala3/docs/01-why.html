    Why green tests lie

    Before any of the machinery makes sense, you need to feel the problem it solves — not as a slogan, but as a specific, ordinary bug that a competent engineer ships on a Tuesday with a fully green build.

    A bug that passed every test

    This is a real defect from the codebase this workflow was built for. A domain-specific language has comparison operators. Some are ordering operators (<, <=, >, >=); some are set operators (IN); some are range operators (BETWEEN). Deep in the evaluator, a private helper converts the broad operator enum into the narrower one an ordering comparison needs.

    Drill. Click anything you think is the defect. There is exactly one. The full test suite is green. 

    enum CmpOp:
  case LT, LTE, GT, GTE, IN, BETWEEN

enum OrderOp:
  case LT, LTE, GT, GTE

private def cmpOpToOrderOp(op: CmpOp): OrderOp =
  op match
    case CmpOp.LT    => OrderOp.LT
    case CmpOp.LTE   => OrderOp.LTE
    case CmpOp.GT    => OrderOp.GT
    case CmpOp.GTE   => OrderOp.GTE
    case other       => OrderOp.LTE

def evaluate(expr: Expr, row: Row): Boolean =
  expr match
    case Expr.Compare(field, op, value) =>
      compareWith(cmpOpToOrderOp(op), row(field), value)
    case Expr.And(l, r) => evaluate(l, row) && evaluate(r, row)
    case Expr.Count(child, bound, op, n) =>
      countMatches(child, row) |> compareCount(op, n)

    The suite was green because every test used an ordering operator. Why would you write evaluate(Compare(x, IN, ...)) when IN belongs to a different code path? The tests covered the intended usage perfectly — and the defect lives precisely where intended usage never goes.

    The failure mode, named

    A catch-all that maps an unrecognised input to a valid output is the single most dangerous line in a codebase, because it converts a crash — loud, immediate, findable — into a wrong answer, which is silent and can persist for years. Note that the compiler was happy: the match is exhaustive. Note that the types were satisfied: OrderOp.LTE is a perfectly good OrderOp. Note that the tests were green.

    Chapter 7 shows the three separate mechanisms this workflow uses to make that line impossible to ship, and chapter 3 shows the spec rule that would have forced the question to be answered before any code was written.

    The oracle problem

    What you just experienced has a name in the literature. To decide whether a test passed, something must know the right answer. That something is called the test oracle. Barr, Harman, McMinn, Shahbaz and Yoo define the oracle problem as the challenge of “distinguishing the corresponding desired, correct behaviour from potentially incorrect behaviour” for a given input — and their survey is essentially a catalogue of the imperfect ways we approximate an oracle when we do not have a perfect one.

    Prior art

    Barr, E. T., Harman, M., McMinn, P., Shahbaz, M., & Yoo, S., “The Oracle Problem in Software Testing: A Survey”, IEEE Transactions on Software Engineering 41(5), 2015. IEEE · free PDF. Their taxonomy — specified oracles, derived oracles, implicit oracles, and the human as oracle of last resort — maps almost one-to-one onto the enforcement mechanisms you will meet in chapter 5.

    Here is the uncomfortable part. When you write a test, you are the oracle: you decide the expected value. Your knowledge of the right answer comes from the specification, from the domain, from a conversation — from somewhere outside the implementation. That outsideness is the whole value. A test written by someone who has just read the implementation and is asking “what does this do?” instead of “what should this do?” is not an oracle at all. It is a mirror.

    Analogy · the surveyor's benchmark

    A surveyor measuring a building's height does not measure it against itself. They measure against a benchmark — a brass plate whose elevation was established independently, ideally by someone else, ideally long ago. If the benchmark were derived from the building, every measurement would be self-consistent and meaningless. A test suite derived from the implementation is a benchmark chiselled into the wall of the building it is meant to measure.

    Three different things we call “correct”

    Most confusion in this area comes from collapsing three genuinely different claims into one word. Keep them apart and much of this workflow becomes obvious.

    ClaimMeansChecked byFails when
    Consistent The code does what its tests say. The test suite. Almost never — this is the claim that is easy to make true.
    Conformant The code does what the specification says. Tests derived from the spec, types, proofs, review. Whenever the tests were derived from the code instead.
    Adequate The specification says what we actually wanted. Humans, examples, prototypes, production feedback. Whenever the spec is confidently wrong.

    This workflow attacks the middle row with everything it has, and is honest that it cannot solve the third. Chapter 5's proof obligations are literally a ledger of conformance evidence; the human gates in chapter 6 and the checkpoint in chapter 8 are where adequacy gets its say.

    Why it is designed this way

    Notice what follows from the table: adding more tests cannot move you from consistent to conformant. If the tests come from the same place the code came from, a thousand of them buy you exactly as much conformance evidence as one. What moves you is independence — a different source, a different mechanism, a different person, a different moment in time. Every ring in chapter 7 is a different axis of independence, which is why the workflow stacks them rather than doubling down on any one.

    Why LLM assistance makes this acute

    The mirror problem is old — TDD's insistence on writing the test first is a 30-year-old answer to it. What is new is the rate and the correlation.

    When an agent implements a feature and then writes tests for it, it is grading its own work, using the same understanding that produced the code. If it misread the spec, the tests encode the misreading and turn it green. The mistakes are not independent; they are perfectly correlated, because they have a single cause. And it happens at a speed no review cadence was designed for.

    Prior art · recent evidence

    A 2026 study of agents resolving real GitHub issues found the volume of agent-written tests correlated only weakly with whether the issue was actually resolved, and that a large share of what agents called “tests” were closer to value-revealing print statements than assertions (arXiv:2602.07900). The spec-driven development literature converges on the same remedy: if the test exists first, written against a specification the agent did not author, the agent must conform to an external target rather than validate its own output (arXiv:2602.00180).

    You have always known not to write the test after the fact “to make coverage go up”. The agent does exactly that, tirelessly, at 200 lines a minute, and its version is more convincing because it is well-formatted and thorough-looking. Your existing instinct is right; it just needs to be turned into a rule a machine can enforce, because your review bandwidth is now the bottleneck.

    The workflow's answer: tests are written from the spec before the implementation exists (chapter 6), and each one must be seen to fail before it is trusted.

    Two error sources are useful only if their failures are independent. Redundancy with correlated failure modes buys nothing — the classic result from reliability engineering, and the reason N-version programming disappointed: independently written implementations still failed together on the hard inputs.

    Code and tests from one agent in one session have a correlation coefficient close to 1. Every device in this workflow — spec-first tests, fresh-context adversarial review, mutation, formal proof, human gates — is an attempt to decorrelate the evidence, not merely to add more of it.

    Security engineering already assumes the artefact under review may be subtly, deliberately wrong, and that a reviewer with the author's mental model will not see it. Hence adversarial review by someone else, hence defence in depth, hence “assume breach”.

    Ring 8 (chapter 7) is that discipline applied to correctness: a reviewer with no implementation context whose job is to prove the code violates the spec while passing the tests. Not to check that it works — to try to show it doesn't.

    What independence actually costs

    If independence is the goal, why doesn't everyone have it? Because each independent source of evidence costs something real, and the costs are paid at different times by different people:

    • Writing the spec first costs thinking before typing — the most expensive kind of work, and the easiest to skip when the code “is basically obvious”.
    • Writing tests from the spec costs the convenience of writing tests against an API you can already see and run.
    • A second reviewer without context costs a context switch and duplicated reading.
    • Mutation, formal proof, model checking cost machine time and, worse, engineer patience.

    A workflow that ignores those costs gets abandoned in week three. So this one prices them explicitly: rings are conditional (chapter 7), human gates are tiered by risk (chapter 8), and the expensive evidence runs last, on final code, so it is never paid twice. Watch for that pattern — it is the difference between a method and a wish.

    The workflow's answer, in one sentence

    The core commitment

    Types and tests are designed BEFORE implementation so they act as an oracle derived from the specification, not a mirror of the generated code — and every claim the spec makes carries an explicit, ranked record of which mechanism keeps it honest.

    Everything else — eight planning artifacts, fourteen apply steps, ten rings, half a dozen scanners — is machinery for making that sentence true under realistic conditions: on a multi-module build, with an agent doing the typing, at a speed where nobody can read everything.
