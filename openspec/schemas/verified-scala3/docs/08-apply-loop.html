    Chapter 8 · Operations

    The apply loop

    Chapter 7 covered the rings themselves. This chapter is the machinery around them: how a spec starts, what makes each diff exact, what gets checked at the end, and why the loop stops dead at a human three times.

    One spec at a time

    The schema states this in a box of block characters, which is unusual for a configuration file and tells you how often it is violated:

    Rule

    The cycle is: implement ONE spec → checkpoint → WAIT → human approves → next spec. Moving to the next spec without explicit approval is a schema violation. “I'll just do the next one since it's simple” is not acceptable. “The user said continue earlier, so I'll keep going” is not acceptable.

    Each spec requires its own approval. No exceptions.

    The reason is not ceremony. Batching converts N approvals into one, and a human reviewing four specs at once reliably approves three of them unread — producing a durable record of scrutiny that did not occur. It also destroys the baseline discipline below: with four specs in one working tree, no diff is attributable to any spec, which silently corrupts mutation targeting, the adversarial review's scope, and the concept delta.

    Step 0 · The baseline, in detail

    Everything downstream depends on getting this right, and it is the step most likely to be skipped because nothing visible happens.

    Why it is designed this way · the baseline is a correctness device

    It looks like bookkeeping; it is the thing that makes four different rings honest. Without a per-spec baseline, “the files this spec changed” is undefined, so mutation mutates the wrong set, the adversarial reviewer reads the wrong diff, and the dependency delta reports a library that a previous spec added. Each of those failures is silent and produces a confident wrong number in the checkpoint — the failure mode this workflow fears most.

    Gate tiering

    Steps 1 and 2 each end in a human stop (chapter 6). One concession exists:

    TierAllowed whenWhat changes
    separate (default)anything elsetwo stops: contract, then oracle
    combinedcomplexity = simple AND proposal risk = low one stop: contract and oracle presented together after step 2

    Both steps still execute in full — tiering changes how many times the human is interrupted, never what is produced. The tier is recorded per spec in implementation-order.md, so it is a decision made deliberately at planning time rather than a shortcut taken under pressure at 5pm.

    Step 12 · The four deltas

    After the rings pass, before the checkpoint, four things are reconciled. This step is where scope creep is caught, and it is almost entirely mechanical.

    1 · Concept delta — the scope-creep check

    new public surface == previous inventory
                    + Concepts Introduced (from the spec)
                    + approved extensions

    Computed by re-running the scanner and diffing against the step-0 snapshot. Anything extra is either added to the spec with human approval, or removed. This is what stops “while I was in there” from accumulating a public API nobody designed.

    2 · Removal audit

    For every field or type removed, find now-orphaned dependents: helper factories, opaque adapters, extension methods that existed only to serve the removed member. Each must be deleted in this change or explicitly retained with rationale.

    Why lint cannot do this for you

    RemoveUnused does not flag public members — it cannot know whether an external consumer uses them. So a helper whose only caller you just deleted compiles forever as dead public API, and the next engineer reads it as an intentional part of the design. The audit is mandatory precisely because the compiler is structurally silent here.

    3 · Build-dependency delta

    git diff <baseline> -- build.sbt project/. Any new library dependency is an unreviewed behaviour source and must be named in the proposal or design, or approved at the checkpoint. The concept delta pins the type surface; this pins the dependency surface.

    4 · Registry and inventory update

    New concepts are appended to the project inventory with provenance (spec:<change>/<spec>), using actual source details rather than planned ones. If the spec altered a registry concept's actions, state or synchronizations, the concept file is updated now and registry-check.sh must pass again — an implementation whose concept files are stale is not complete.

    Step 13 · The checkpoint

    Mark progress, regenerate tasks.md from the progress file, commit the spec, then present a fixed structure: 

    ## ✓ Spec 2/5 complete: cross-run-memory-example

**Commit:** a1b2c3d (baseline was 9f8e7d6)
**Files changed:** …
**Rings:** R0 ✅ R1 ✅ R2 ⏭ R3 ✅ R4 ⏭ R8 ✅ R5 ✅ R6 ⏭ R7 ⏭ R9 ⏭
**Oracle polarity:** 11 red→green confirmed, 3 green-by-design held
**Cross-module regression:** adk4s-orchestration, adk4s-examples — pass
**Exhaustiveness escalation:** -Wconf active
**Adversarial review:** PASS (fresh-context: yes)
**Proof obligations:** all enforced except 3 manually-reviewed: …
**Concepts added to inventory:** FileBackedAgentMemory, StoragePath
**Concept registry files updated:** memory-aware-runner.md
**Concept delta (scanner diff):** exactly as committed
**Build-dependency delta:** none
**Design decisions made:** …

⏸  Waiting for your review before starting spec 3: …

    Two things about this format are worth noticing. First, it is fixed: the same fields every time, so a reader learns where to look and notices an empty field. Second, it foregrounds what was not mechanically enforced — skipped rings, manually-reviewed obligations, PARTIAL verdicts. The checkpoint is optimised for the human to find the soft spots quickly, not to look impressive.

    Failure mode · a self-report at the highest-leverage moment

    Until schema v12 the Rings: line was composed by the agent from memory of what it believed it had run. Nothing compared that prose against what actually happened — the checkpoint that exists specifically so a human can trust the summary was, itself, unverified. A real instance: a spec's own tracker recorded five green rings while a ledger of the commands actually run showed no evidence for two of them.

    Where scanner/checkpoint.sh exists (schema v12+, shipped with the evidence-ledger / chain-state / checkpoint-from-ledger specs — chapter 12 covers the whole mechanism), the Rings line is generated, not authored. Every ring result traces to a row an earlier step appended to an append-only evidence ledger — command, exit status, baseline — and a ring with no matching row is rendered as having no recorded evidence, never quietly folded into a passing summary. tasks.md's checkboxes are regenerated from the same tracker the same way, so the two files cannot independently drift. Before that tooling exists in a given schema version, the line is still hand-composed — the format is unchanged, only its provenance is.

    Rule · the commit is the checkpoint's identity

    Committing at step 13 is not a convenience. It (a) makes every per-spec diff exact, (b) gives the next spec its baseline, (c) makes the work bisectable, and (d) means an approved checkpoint refers to an immutable state rather than a working tree that keeps moving. If a project forbids per-spec commits, an alternative baseline mechanism must be recorded in the capability profile — but a baseline there must be.

    When the human asks for changes

    The re-run rules are precise, and they matter because “just re-run everything” is expensive and “just re-run the tests” is wrong:

    Change requestedRe-run fromNote
    Source changeRing 0and always Ring 8, then Ring 5 — mutation must see final code
    New test onlyRing 3oracle changed → re-present the oracle gate
    Package moveRing 2layer rules may now be violated
    Serialization changeRing 4 includedfixtures must still decode
    Contract signature changegate 1re-present the typed contract for approval first

    Then the spec's commit is amended and the checkpoint re-presented. The rule underneath all of these: any artifact that was approved and has now changed must be re-approved.

    Failure handling

    The loop specifies what to do when things go wrong, which is what keeps an agent from improvising:

    SituationAction
    Dirty tree at step 0STOP, resolve with human
    Proof obligation with no mechanismSTOP, fix the spec
    Concept missing from inventorySTOP, ask which of three causes applies
    MUST-CONFIRM itemSTOP, ask for authoritative data
    RED test passes before implementationbroken oracle — fix before the gate
    Ring 0 fails after 3 iterationsSTOP, present the errors
    Property falsified after 3 fixesSTOP, present counterexample and seed
    Concurrency test flakesRing 3 FAILURE — fix the race, never re-run away
    Ring 8 FAILfix before Ring 5; re-run affected rings
    Unapproved new build dependencyremove, or get approval at checkpoint
    Two specs modify the same fileSTOP, ask the human
    Why so many explicit STOPs

    An agent's default behaviour under uncertainty is to proceed plausibly — pick the likeliest interpretation and continue, because that is what generates fluent output. Every STOP above marks a place where proceeding plausibly produces work that looks finished and is built on an unverified assumption. Naming them explicitly converts the default from “guess and continue” into “ask”, which is the single highest-leverage change you can make to an agentic workflow.

    The loop as an economic system

    Machine time is cheap and getting cheaper; human review attention is fixed and expensive. Every design choice in this loop follows from that asymmetry: mechanical checks run first and unattended, humans are consulted at three points chosen for leverage, tiering removes stops where risk is low, and the checkpoint format foregrounds exactly the residual risks a human must judge.

    The failure mode being avoided is review fatigue: ask for approval too often on things too trivial and you train the reviewer to approve reflexively — which silently deletes all three gates at once.

    Lean and continuous-delivery practice says: small batches, fast feedback, stop the line on defect. One spec per loop is a batch size of one. The three gates are the andon cord. The rings are the automated inspection stations, ordered cheapest-first so defects are caught before value is added on top of them.

    The per-spec commit is what makes the batch real: an amendable, bisectable unit that either passed everything or is still open. Without it you have a large batch wearing the costume of a small one.

    Check yourself

    Before moving on, you should be able to say

    • Why the baseline SHA is a correctness device, not bookkeeping.
    • All four deltas reconciled at step 12 and the bug class each catches.
    • Why the removal audit cannot be delegated to lint.
    • What the checkpoint deliberately foregrounds, and why.
    • Which rings re-run after a source change, and why Ring 5 must be last.
