    Writing specs that can be verified

    A specification in this workflow is not documentation. It is the oracle — the external source of truth that tests, types and reviews are all derived from. That job imposes requirements on how it is written, and most of this chapter is those requirements and why each one exists.

    What kind of document is this?

    Three properties distinguish a verified-scala3 spec from the design doc you are used to.

    It is a delta. Sections are headed ## ADDED Requirements, ## MODIFIED Requirements, ## REMOVED Requirements. You describe the change to the world, not the world. This keeps specs small enough to verify exhaustively, and it makes review answer the right question — “is this change correct?” rather than “is this 40-page document still accurate?”

    It is per-capability. One file per capability under specs/<capability>/spec.md. A capability is a coherent slice of behaviour that can be implemented and verified independently, which is also the unit of the apply loop and of human approval.

    It is machine-checked. Eighteen lint checks run over it, seven of them mechanically. A spec that fails blocks the whole change from proceeding. This is unusual and it is the point: prose that cannot be checked is prose that quietly drifts from the code.

    The sections, in order, and which are optional:

    The requirement — the atom of a spec

    Every requirement has the same three-part shape:

    ### Requirement: Frozen episodes are never returned by recall

The system SHALL exclude episodes whose frozen flag is set from every
recall result.                          ← 1. normative statement (SHALL/MUST)

**Given** a memory containing one frozen and one unfrozen episode
**When**  recall is called with a query matching both
**Then**  only the unfrozen episode is returned
                                        ← 2. the claim, in observable form

#### Scenario: Frozen episode is excluded even when it scores highest

**Given** a frozen episode scoring 0.99 and an unfrozen one scoring 0.10
**When**  recall("blue", k = 2) is called
**Then**  the result contains only the unfrozen episode
                                        ← 3. scenarios: concrete, testable

    Part 1 · the normative statement

    A single sentence containing SHALL or MUST, placed between the heading and the first **Given**. This is mechanically checked (lint F1) and also required by openspec validate --strict.

    Prior art · why SHALL

    The modal-verb convention comes from RFC 2119 and from systems and aerospace requirements engineering, where “shall” marks a binding obligation and “should” marks a recommendation. The discipline it enforces is subtle but real: you cannot write a SHALL sentence without deciding who is obliged to do what. Sentences like “the cache is updated” — passive, agentless — do not survive the transformation.

    The closest relative is EARS (Easy Approach to Requirements Syntax), developed by Alistair Mavin and colleagues at Rolls-Royce while analysing airworthiness regulations for jet-engine control, published at RE'09. EARS constrains requirements to a handful of templates: ubiquitous (“The <system> shall …”), event-driven (“When <trigger>, the <system> shall …”), state-driven (“While <state>, …”), unwanted behaviour (“If <condition>, then …”), and optional feature. Original paper (PDF).

    This workflow uses EARS directly for Ring 9 temporal properties, and its general spirit — a fixed grammar removes ambiguity cheaply — everywhere else. Given/When/Then is essentially EARS's event-driven pattern decomposed into labelled parts, which is why the two feel so similar.

    Part 2 · Given / When / Then

    Precondition, trigger, outcome. The rule that does the real work is about the Then:

    Rule · every Then must be observable

    A Then names a return value, a persisted event, an emitted message, or an error value — something a test can look at from outside. “The system handles it correctly” is a FAIL. “The cache is warmed” is a FAIL unless warmth is observable. If you cannot say how you would see it, you cannot say whether it happened.

    Analogy · operationalisation in science

    An experimental psychologist may not write “subjects became anxious”; they write “subjects' self-reported anxiety on the STAI scale increased by ≥ 8 points”. The construct is turned into a measurement procedure. The observability rule is exactly operationalisation: an unobservable Then is an unfalsifiable hypothesis, and an unfalsifiable hypothesis cannot function as an oracle.

    Part 3 · scenarios

    Concrete instances with real values. Each becomes one test, named after the scenario heading, in step 2 of the apply loop. The schema expects at least a happy path plus an error or edge case; several rules below force particular scenarios to exist.

    The seven rules that catch real defects

    These are the spec rules that exist because something went wrong. Each one is a scar.

    1 · No vague words

    valid, correct, fast, reasonable, appropriate — flagged by the linter (W1) unless a concrete definition sits next to them. “Returns valid results” names nothing an oracle can check; every reader supplies their own definition, and the agent supplies the one that makes its implementation pass.

    2 · Every error path specified

    If a requirement can fail, the spec says what failure looks like. Unspecified failure behaviour is where fallbacks breed — and chapter 1 showed what a fallback costs.

    3 · The adversarial rule

    Rule · negative requirements need forbidden inputs

    Every requirement containing only, never or must not must have at least one scenario whose input the requirement forbids. Positive examples alone do not pin a negative requirement (lint F2 / W3).

    “Frozen episodes are never returned” is satisfied by an implementation that returns nothing at all. Only a scenario that feeds in a frozen episode which would otherwise rank first distinguishes the correct implementation from the lazy one. This is Popper's asymmetry in miniature: universal negatives are refuted by instances, not confirmed by absence.

    4 · MUST-CONFIRM for external data

    Any classification table, code mapping or value domain whose authority lives outside the repo is marked MUST-CONFIRM — do not invent with a pointer to the real source. The apply phase then stops and asks.

    Failure mode · plausible fabrication

    Asked for a spec involving, say, ISO currency minor units or a regulatory status-code table, a language model will produce a beautifully formatted, entirely plausible, partially wrong table — and every test derived from it will pass, because the tests come from the same table. This is the consistent-but-not-conformant trap in its purest form: the whole stack agrees with itself and disagrees with reality. MUST-CONFIRM is the marker that converts a silent invention into a blocking question.

    5 · Type-widening impact

    If a spec aliases a public type to a richer one, or otherwise grows its reachable variant set, it must list every downstream pattern match with a catch-all arm and state how each behaves for the new variants.

    This is subtle enough to deserve emphasis: aliasing a type is an enum extension even though no variant is added in source. No file changes, no diff to review — and every case _ => downstream silently starts absorbing cases it has never seen. It is chapter 1's bug arriving by a route that leaves no fingerprints.

    6 · Error-variant feasibility

    If a Then asserts that a specific error variant is returned, that must be type-feasible against the producing API. A handler typed Either[String, R] cannot return a structured ToolCallError. Resolve it in the spec — amend the requirement or the signature — rather than discovering it mid-implementation, where the temptation is to weaken the test instead.

    7 · Altitude and concurrency

    Two rules from later versions of the schema. Altitude (when a behavioural registry exists): requirements use behavioural vocabulary; module names, error classes and build commands go in ## Implementation Anchors, never inside a Given/When/Then — so a refactor does not invalidate the spec (chapter 4). Concurrency: a requirement about concurrent behaviour must name a deterministic observable — an ordering guarantee, a final state, an emitted-event set — never a wall-clock expectation like “within 100 ms”, which produces flaky tests that get muted, which is how concurrency bugs survive.

    Properties: the other half of the spec

    Scenarios pin specific points; properties pin the whole domain. Every code-changing spec needs a ## Properties (Ring 3) section, and every property must declare its generator strategy (lint F3). 

    ### Property: recall-ordering

**Invariant**: for any memory and any query, returned hits are ordered
by descending score.

**Generator strategy**: genMemory — constructive, sizes 0..20, includes
empty and all-equal-score cases — cover 20% "ties".

```
forAll(genMemory, genQuery) { (mem, q) =>
  val hits = mem.recall(q, k = 10)
  hits.zip(hits.tail).forall((a, b) => a.score >= b.score)
}
```
    Why the generator strategy is mandatory

    A property is only as strong as the inputs it sees. forAll over a generator that never produces an empty collection has not tested the empty case, no matter how many thousand runs it makes — and the failure is invisible, because the property passes.

    So the spec declares: which generator, constructive or filtered (constructive preferred — heavy filtering silently discards cases), which edge cases it covers, and which classification labels make coverage visible. Where the framework supports coverage assertions — Hedgehog's cover fails the test when a label's percentage is unmet — a conditioned property must carry one. That converts “I hope the interesting case occurred” into a check.

    Deep dive · why this project's stack uses Hedgehog, and what changesoptional

    ScalaCheck derives generators from an Arbitrary typeclass and takes shrinkers as separate functions. Hedgehog has no typeclass — generators are ordinary values you pass explicitly — and shrinking is integrated: shrinks are derived from the generator, so they obey the generator's invariants by construction.

    That difference matters for this workflow. With separate shrinkers, minimising a counterexample can produce a value your generator would never have produced — an input that violates a domain invariant, sending you to debug a case that cannot occur. Integrated shrinking cannot do that. The trade-offs are real in both directions (integrated shrinking is slower and sometimes yields larger counterexamples; Hedgehog makes you write every generator by hand). See Well-Typed on integrated vs manual shrinking and a migration report.

    The workflow itself is framework-agnostic: the capability profile records what the project actually uses, and the oracle is generated for that. What is not negotiable is that the strategy is declared in the spec, so a reviewer can judge coverage before any test exists.

    Three ways to look at the same rules

    Read the rules as pressure toward making illegal states unrepresentable. The observability rule pushes behaviour to the API surface where types live. The type-widening rule is about variant sets. The error-variant feasibility rule is literally type-checking the prose.

    The spec is where you notice that an invariant could be a type. Every time it can, the resulting proof obligation climbs to the top of the mechanism ladder (chapter 5) and stops needing tests at all — which is the cheapest verification there is.

    Read the spec as a test plan written before the code, because that is exactly what step 2 turns it into: one test per scenario, one property per invariant, one assertDoesNotCompile per compile-negative obligation.

    Every rule here removes an ambiguity that would otherwise be resolved at test-writing time — which is precisely when resolving it wrongly is invisible, because the test then agrees with the code by construction.

    Read the rules as a checklist for the question “could I tell whether this is implemented correctly?” If a Then is unobservable, no. If a negative requirement has no forbidden-input scenario, no. If a table came from nowhere, no.

    This is why lint FAIL blocks the change: review capacity is the scarcest resource in the loop, and an ambiguous spec silently converts a five-minute review into an hour of archaeology — or, more often, into an approval that did not really happen.
