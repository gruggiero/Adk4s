    A tutorial in twelve chapters

    Building software that is correct on purpose

    You are an experienced Scala engineer. You know types, property tests, and effect systems. What you may not yet have is a method that makes an LLM-assisted codebase demonstrably correct rather than plausibly correct. That is what verified-scala3 is, and this tutorial teaches it from first principles.

    Schema version 12 · Reading time ≈ 4.5 hours end to end · Interactive: every chapter has drills, and chapters 3 and 5 embed a working port of the real spec-lint.sh you can paste specs into.

    The thesis, in one paragraph

    A passing test suite is not evidence that code matches its specification — it is evidence that code matches its tests. Those are the same thing only when the tests were derived from the specification by someone who could not see the implementation. When an agent writes the code and then writes the tests, that condition is violated in the worst possible way: the tests inherit the implementation's misunderstandings and then certify them green. verified-scala3 is a workflow whose entire purpose is to restore the independence of the oracle — and then to stack additional, mutually-independent forms of evidence on top of it, cheapest and strongest first.

    The shape of the idea

    Everything in this workflow is an answer to one question: “what would have to be true for me to believe this code is right, and how do I check that mechanically rather than by feeling?” Types, specs, obligations, rings, gates — every artifact you will meet is a different answer to that question, arranged so that they fail independently.

    Who this is for

    The intended reader is a strong Scala 3 developer who is new to specification-driven, verification-first development. You should be comfortable with sealed traits and exhaustive matching, opaque types, cats-effect or an equivalent, and at least the idea of property-based testing. You do not need any prior exposure to formal methods, requirements engineering, OpenSpec, or agentic workflows — all of that is built up here from zero.

    After chapter 5 you can
    • write a spec whose every claim has a named, ranked defence
    • read a proof-obligation table and see what it does not guarantee
    • run the mechanical lints and interpret F1–F10
    After chapter 12 you can
    • run a change end to end through the ring pipeline
    • adopt the workflow in a project that has never used it
    • tell which rings are earning their cost in your codebase
    • enforce the checks so they run whether or not anyone remembers
    • tell the difference between a claim that is bound, resolved, and one that is actually discharged
    • capture evidence as a side effect of running a ring (ledger.sh run) and replay it later (ledger.sh verify)

    Conventions in these pages

    Callouts carry meaning; learn the five you will meet constantly:

    Rule

    A binding rule of the workflow. If you break it, some machine check or human gate is supposed to catch you. These are quoted from the schema, not invented for the tutorial.

    Failure mode

    A specific way projects get this wrong — usually one that produces green builds and false confidence, which is the only kind of wrong this workflow really fears.

    Why it is designed this way

    The reasoning behind a rule. You can follow the workflow without these; you cannot adapt it without them.

    Analogy

    A bridge from something you already know — accounting, surveying, aviation, science — to the concept at hand.

    Prior art

    Where the idea comes from in the literature, with a citation you can follow. Almost nothing here is new; the contribution is the assembly.

    You will also meet deep dives (collapsed by default — skip them on a first pass), viewpoint tabs that explain the same concept from two or three angles, and drills that ask you to find the bug before the text tells you where it is. Do the drills. The entire discipline is a trained reflex for noticing what looks fine.

    One page you may want open alongside

    This tutorial teaches the workflow; the workflow itself lives in openspec/schemas/verified-scala3/ next to these docs — schema.yaml (the rules), templates/ (the artifact skeletons), scanner/ (the mechanical checks), and skills/ (the agent instructions). Where a chapter states a rule, it is quoting one of those files, and you can go read the original.

    Before you start chapter 1

    • You do not need the tooling installed to read — every drill runs in the page.
    • If you want to run the real checks as you go, you need bash, git, and optionally scala-cli; chapter 9 covers setup.
    • Keep a real change of your own in mind. The material lands much harder when you are mentally applying it to code you know.
