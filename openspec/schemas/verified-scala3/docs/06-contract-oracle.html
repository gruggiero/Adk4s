    Chapter 6 · The gates

    Typed contract & test oracle

    Two artifacts stand between a lint-clean spec and any implementation, each followed by a human stop. They exist because the two cheapest moments to be wrong are before the types are fixed and before the tests can see the code.

    Why these two, in this order

    Think about what an implementation can silently get wrong, and when each error becomes expensive to fix:

    Wrong thingCost if caught at contract timeCost if caught after implementation
    The error type cannot express the specified failureedit one signaturerewrite every call site and every test that asserted the wrong error
    A concept was recreated instead of importeddelete a declarationmigrate, deprecate, write conversions, live with both
    The tests encode the implementation's misreading—never caught; ships green

    The third row is the one with no recovery, which is why the oracle gate exists at all. The order — types, then tests, then code — follows from dependency: tests must compile against something, and if that something is the implementation, the tests inherit its shape. Compiling them against a contract of ??? bodies breaks that inheritance while still giving the type-checker's help.

    Step 1 · The typed contract

    A compile-only file containing the change's type-level commitments, with no behaviour at all: 

    // adk4s-memory-api/src/test/scala/org/adk4s/memory/typecontract/
//   FileBackedMemoryTypeContract.scala

import org.adk4s.memory.{ Episode, MemoryHit, TemporalScope }  // reused, not recreated

opaque type StoragePath = String
object StoragePath:
  def parse(raw: String): Either[MemoryError, StoragePath] = ???   // smart constructor
  extension (p: StoragePath) def value: String = p

enum MemoryError:                       // the error algebra, decided up front
  case StorageUnreadable(path: StoragePath, cause: String)
  case MalformedRecord(line: Int)

trait FileBackedAgentMemory[F[_]]:
  def remember(e: Episode): F[Either[MemoryError, Unit]] = ???
  def recall(q: String, k: Int, scope: Option[TemporalScope]): F[List[MemoryHit]] = ???
    Rule · placement is what makes it real

    The contract lives in the owning module's test sources, so sbt <module>/Test/compile compiles it against the real project classpath. Files under openspec/changes/… are not part of the sbt source graph: writing the contract there produces a document that looks type-checked and is not. That is a false confidence generator, and the schema calls it out by name.

    Compiling it is not ceremony. It is the step that catches: a package that doesn't exist, a concept whose real signature differs from the inventory's claim, a method name already taken, an error enum that cannot represent what the spec demands, a variance or higher-kinded mistake. All of these are cheap now and expensive later.

    What the human is asked at gate 1

    Not “is this code right?” — there is no code. The questions are: are these the right concepts? Is the error algebra complete and at the right granularity? Are the signatures honest about effects and failure? Does anything here duplicate something that exists?

    Why it is designed this way · reviewing a surface, not a solution

    A type surface is small, dense in decisions, and readable in minutes. A finished implementation is large, mostly mechanical, and reviewers unconsciously optimise for “does it look plausible” rather than “is this the right shape”. Worse, by then the reviewer faces sunk cost: rejecting the type design means discarding working code, so the reviewer rationalises. Gate 1 buys the decision before the cost exists.

    After approval: the contract becomes a permanent assertion

    Once implementation lands, declarations are promoted into main sources — and the contract file is not deleted. It is converted into an API conformance assertion: 

    // signatures pinned exactly as approved — zero runtime cost,
// breaks Test/compile the day someone drifts
val rememberSig: Episode => IO[Either[MemoryError, Unit]] =
  memory.remember

val recallSig: (String, Int, Option[TemporalScope]) => IO[List[MemoryHit]] =
  memory.recall

// plus the compile-negative obligations from the spec
compileErrors("""StoragePath("")""")   // must not construct directly

    “Keep the approved signatures” goes from prose nobody re-checks to a compiler-enforced fact. If someone later adds a parameter or widens a return type, the build fails in the file whose entire purpose is to notice.

    Step 2 · The test oracle

    Now the tests — written from the spec and the approved contract only, before any implementation exists.

    Rule · derived from the spec, never from bodies

    One test per scenario, named after the scenario heading. One property per declared invariant, using the generator strategy the spec declared. Model-based tests where the spec declares them. Compile-negative obligations become assertDoesNotCompile / compileErrors. Every test cites its source: // spec: <name> — Scenario: <heading>. Reading implementation method bodies to decide what to assert is forbidden, even when retro-fitting.

    Analogy · pre-registration

    Empirical science had a crisis with results that would not replicate. A major cause was analysing data first and forming the hypothesis after — HARKing — which turns noise into a finding while feeling like discovery. The remedy was pre-registration: publish the hypothesis and the analysis plan before collecting data, so the prediction cannot be quietly reshaped to fit what you saw. The test oracle is pre-registration for software. Writing tests after the implementation is HARKing with a green checkmark.

    Oracle polarity — proving the oracle can fail

    Here is the check most teams have never seen, and it costs one test run. After the oracle compiles, run it — before any implementation — and classify every test:

    RED

    Asserts new behaviour. Must fail now. A red-classified test that passes before the implementation exists is proving nothing: it is vacuous, tautological, or asserting behaviour that already existed. Fix it before the gate.

    GREEN-BY-DESIGN

    Behaviour-preservation tests for a refactor. Must pass now, against the old code, and still pass after. Their pre-implementation pass is their evidential value — it proves they describe the behaviour being preserved rather than the behaviour being written.

    A test that cannot be classified does not enter the oracle. The polarity table (| Test | Polarity | Pre-impl result |) is part of the gate presentation, and step 6 confirms every RED went green.

    Why it is designed this way

    “Tests fail first” is TDD folklore, usually honoured in spirit. This workflow makes it a recorded artifact for a specific reason: an agent writing 40 tests in one pass will occasionally write one that asserts nothing (assert(result != null)), one that tests a helper rather than the requirement, and one that duplicates an existing test. All three are green from birth. Nothing else in the pipeline notices — mutation testing comes closest but runs much later and only over changed production files.

    Making redness an explicit, per-test claim converts a silent class of dead tests into a gate failure at the cheapest possible moment.

    Faithfulness: two ways an oracle gets quietly weakened

    Once implementation begins, the oracle is under pressure — every failing test is friction. The schema names both forms of tampering:

    Oracle faithfulness. A test asserting a spec-named error variant must assert that variant, exactly. Loosening it to .toString.contains("frozen") or an || of substring checks is forbidden. If the implementation cannot produce the named variant, the spec or the signature changes — re-approved at the gate — never the oracle. Substring checks are legitimate only for human-readable message text, never as a substitute for a structured variant.

    Generator faithfulness. Generators are part of the approved oracle. Narrowing one after approval — adding a filter, tightening a Range, dropping an edge case, swapping a constructive generator for a narrower one — is tampering exactly like loosening an assertion, and needs re-approval.

    Failure mode · the property that stopped seeing the bug

    A property fails on the empty list. The tempting fix is one character: genList.filter(_.nonEmpty). The property text is unchanged, the suite goes green, the reviewer sees a passing test whose description still claims “for any list”. Nothing in a diff review looks wrong. This is why the rule is stated at the level of the oracle rather than assertions: the generator is half the claim.

    Which of these edits is tampering?

    The three coverage tables

    The oracle gate presents three cross-references, re-verified at step 6:

    TableBindsCatches
    ARequirement / Scenario ↔ Testa scenario nobody implemented
    BConcept ↔ Test reference a concept the spec claims to use or introduce that appears in no executable test code — comments do not count
    CProof obligation ↔ Test an obligation whose declared mechanism is a test, with no test

    Table C is where chapter 5's ledger becomes executable: every obligation saying “property test” must now name the property. At step 6, zero ❌ rows may remain.

    Concurrency deserves its own rule

    Scenarios involving concurrency, timeouts, cancellation or interruption use the detected deterministic test kit — for cats-effect, TestControl, which runs an IO program against a simulated clock so “after 30 seconds” is instant and exact. Assertions name deterministic observables: ordering, final state, emitted-event set. Never wall-clock timing.

    These tests are also tagged, because step 6 runs them twenty times. A test that passes 19 times out of 20 is not a flaky test; it is a race condition with a 5% detection rate, and the workflow treats an intermittent failure as a Ring 3 failure to fix — never as noise to re-run away.

    Where TDD ends and this begins

    TDD's red-green-refactor gives you the discipline of failing first, but the test's content comes from the developer's head, one example at a time, interleaved with implementation. That interleaving is exactly the correlation this workflow removes.

    Differences: the source is a reviewed spec, not an idea; the whole oracle is written and approved in one batch before any code; redness is a recorded classification, not a moment; and generators plus obligations extend coverage from examples to domains. TDD is the ancestor; this is TDD with the oracle externalised and audited.

    Design by contract (Eiffel, and require/ensuring in Scala) puts pre- and postconditions in the code, checked at runtime or by a prover. The typed contract here is a different animal: it fixes the type surface before behaviour exists.

    They compose — Ring 6 takes the spec's Formal Contracts section and turns exactly those pre/postconditions into machine-checked proofs on pure functions. Think of the typed contract as the signature-level contract and Ring 6 as the value-level one.

    “Type-driven development” — sketch types, let them guide the implementation — is close in spirit, and Idris-style development is its purest form. What is added here is the gate: a human approves the surface, and the surface is then pinned by a conformance assertion that fails the build on drift.

    Without the pin, type-first design decays exactly the way documentation does: the sketch was right on Tuesday, the implementation moved on Thursday, and nothing noticed.

    The economics of the two gates

    Three human stops per spec is a real tax, and the workflow prices it. On a spec whose complexity is simple and whose proposal risk is low, the two inner gates may be tiered: both steps execute fully, but their outputs are presented together at one stop after step 2. Everything else keeps two.

    Why tiering is a correctness feature, not a shortcut

    A gate the human has stopped reading is worse than no gate, because it produces a durable record of an approval that never happened — and later readers, including the agent, treat that record as evidence. Spending attention where risk is concentrated keeps the remaining gates real. This is the same reasoning that makes manual-review obligations explicit rather than hidden: the workflow would rather show you a small number of true signals than a large number of ceremonial ones.

    Check yourself

    Before moving on, you should be able to say

    • Why types come before tests and tests before code, in dependency terms.
    • Why contract placement in test sources is a correctness requirement.
    • What oracle polarity is and what a RED test passing early means.
    • Both forms of oracle tampering and why generators count as the oracle.
    • What the three coverage tables bind, and why table B excludes comments.
