    Chapter 10 · Synthesis

    In practice

    One real change, end to end, with its real artifacts and real numbers — then the anti-patterns, an adoption path, and an honest account of what this workflow still cannot do.

    The change: proof of life for durable memory

    add-cross-run-memory-example, a genuine change in this repository. Its proposal opens with the gap it closes:

    “ADK4S ships a complete durable-memory stack … but no example exercises it. ReactMemoryExample demonstrates only in-conversation memory, which dies with the process. The durable-memory stack has no proof of life: no runnable artifact shows an agent taught a fact in one process recalling it in a completely separate process.”

    Note what that paragraph does: it states an observable gap. Not “memory needs better docs” but “nothing demonstrates cross-process recall”. The verification target is visible from the first sentence.

    Planning artifacts, as they actually came out

    ArtifactWhat it decided
    proposal Risk low. Rings: 0, 1, 3, 4, 8 apply; 5 skipped (example code — the laws suite is the safety net); 6, 7, 9 not applicable. Ring 3 mandatory.
    capability-check Confirmed munit + Hedgehog, cats-effect 3.7.0, no telemetry stack. Recorded that TestControl is available but not required — the file-backed memory is single-writer, the decorator sequential. An explicit “no concurrency here” finding, not an omission.
    inventory-check Verified reuse of AgentMemory, Episode, MemoryHit, TemporalScope, MemoryAwareRunner. Introduced: FileBackedAgentMemory.
    spec 8 requirements, 4 properties, 23 proof obligations.
    spec-lint PASS.
    implementation-order One spec. Complexity simple + risk low ⇒ human gate tier combined.

    Step 0 · the baseline, for real

    - BASELINE SHA: 0e1e4593107f05e6db6f680c1f06e8ee9c4a7309
  (recorded 2026-07-19; working tree clean after spec commit)
- registry-check.sh: OK (611 tokens verified,
  2 pre-existing weak bindings in react-agent.md)
- no PUBLIC-TYPE-CHANGE IMPACT SCAN
  (spec adds new types, does not widen a sealed ADT)

    The last line is worth pausing on. The impact scan was considered and found not to apply, and that judgement is recorded. A future reader — or a Ring 8 reviewer — can see the question was asked. Silence would have been indistinguishable from forgetting.

    The combined gate: contract and oracle together

    Because the spec was simple and low risk, both steps executed in full but the human stopped once. The polarity result is the most instructive line in the whole change: 

    ORACLE POLARITY: 7 RED against signature-only FileBackedAgentMemory,
                 1 GREEN-BY-DESIGN (adversarial broken-double test)
    Why that one green test is not a failure of the process

    Seven tests asserted behaviour that did not exist yet — they failed, as they must. The eighth runs AgentMemoryLaws against a deliberately broken memory double and asserts that at least one law fails. That test passes before the real implementation exists, and correctly so: it is not testing the new memory, it is testing that the laws suite can detect a violation at all. A laws suite that passes everything is decorative. Classifying it green-by-design forces you to say out loud why it should pass — which is exactly the reasoning that distinguishes it from a vacuous test.

    Rings, with real reasoning

    RingVerdict and why
    R0✅ — exhaustiveness escalation active but not exercised: no sealed ADT extended.
    R1✅ — Scalafix + WartRemover (examples use the relaxed set, as edge code) + scalafmt.
    R2⚠️ advisory — no custom architecture rules installed; examples.* may import anything, so no new purity boundary. Stated, not hidden.
    R3✅ — laws suite + 4 Hedgehog properties + a cross-run scenario test. No concurrent behaviour, so TestControl was not required — a decision, recorded.
    R4✅ manual — the change introduces a JSON-lines persistence format, so a reload-across-instances property was added: write with one instance, recall with a fresh instance at the same path.
    R5⏸ skipped — example code; the laws suite is the mutation-equivalent net. Recorded in the proposal, with impact.
    R6/R7/R9⏸ not applicable — effectful example wiring, no distributed invariants, no telemetry stack.
    R8✅ — fresh-context review of three specific risks: does the mock answer from injected context or from a script; do the two smoke-test stacks share only a temp directory; does the file-backed memory honour all four laws in spirit.

    Read the R4 row again. The workflow noticed that “write JSON lines to a file” is a persistence format, and demanded a cross-instance property for it — in an example. That is the compatibility ring earning its place on a change nobody would have thought needed it.

    Anti-patterns

    Every one of these has been observed, several in this very repository.

    Anti-patternLooks likeCosts you
    The retro-fitted oracle Implementation lands first, tests “from the spec” written after. Everything. The tests are a mirror; the rest of the workflow now certifies a reflection.
    Coverage theatre A 40-row obligations table, one row per requirement, all “property test”. Reachability without strength. Chapter 5's ladder exists so you climb it, not so you fill the column.
    The muted flake “It's just timing, retry in CI.” A race condition with a 5% detection rate, now with the detector disabled.
    The defensive fix Ring 8 finds a bad input path; the fix adds a fallback so it “can't crash”. Chapter 1's exact bug, deliberately installed. The fix is type-level prevention or explicit rejection.
    The generous generator A property fails; the generator gets a filter. A property whose text over-claims what it tests, and a real finding discarded.
    Batch approval “Approve specs 3–6, they're all similar.” Three unread approvals recorded as scrutiny, and four specs sharing one baseline.
    The stale profile Capability profile written once, never re-verified. Tests generated for a framework you no longer use; rings claimed that no longer exist.
    Idealised registry Concept files describe the architecture you wish you had. A confident second source of truth that disagrees with the code.
    The invented table A plausible mapping of codes/units/statuses, unmarked. Self-consistent, externally wrong, with tests agreeing. Mark it MUST-CONFIRM.

    Adopting this on a project that has none of it

    Do not start by writing eight artifacts. Start by making the cheap checks true, then add ceremony only where it buys evidence.

    The adoption principle

    Each step above is independently valuable and none requires the next. That is deliberate: a method you must adopt wholesale is a method that gets abandoned wholesale on the first sprint where it is inconvenient. Strict compilation is worth having even if you never write a spec; the inventory is worth having even if you never adopt the rings.

    What this workflow still cannot do

    A method that hides its limits is doing the thing it warns you about.

    • It cannot tell you the requirement is wrong. Chapter 1's adequacy row is untouched. A perfectly enforced obligation faithfully protects a mistaken claim, and no ring will ever object.
    • The artifact is checked for existence, not content. Since v9, Step 12 verifies the named suite resolves to a tracked file (F9) — this caught a suite in this very repository that had never been written — but nothing checks that it asserts that row.
    • Ordinal references remain legal (now W4 on any occurrence, not a FAIL), so a spec that opts into positional links can still be silently re-pointed by reordering.
    • Mechanism strength is nudged, not enforced. W5 flags an impossibility claim defended only by tests, and tier-justified: silences it — an honest escape hatch that an unmotivated author can always take.
    • It costs real time. Two extra gates, an obligations table, and a fixed apply sequence per spec. On genuinely trivial work, that overhead can exceed the value — which is what waivers, tiering and conditional rings exist to manage, and what your judgement exists to decide.
    • It assumes a human who reads. Every mechanism eventually reports to a checkpoint. If that human rubber-stamps, the workflow degrades to an elaborate way of generating documentation about unexamined code.

    The through-line

    If you retain one sentence from ten chapters, retain this: evidence is only worth what its independence is worth. Everything here is a consequence.

    DeviceWhat it decorrelates

    Oracle polarity“the test passes” from “the test can fail”

    You have finished the core of the tutorial

    You should now be able to:

    • Explain why a green suite is not conformance evidence, and what would be.
    • Write a spec that survives lint, and say what each rule prevents.
    • Build a proof-obligations table and defend every mechanism choice.
    • Run a spec through the apply loop and read its checkpoint critically.
    • Choose rings for a change and justify each omission.
    • Adopt the workflow incrementally without stalling a project.

    The last skill is the one that matters most: knowing which parts to apply when, and being honest — out loud, in an artifact — about what you skipped.

    One thing remains, and it is the question this whole chapter quietly assumed away: every check you have just seen runs only because somebody chose to run it. Chapter 11 removes the choice.
