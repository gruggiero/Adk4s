    Chapter 5 · The keystone

    Proof obligations

    If you learn one thing from this tutorial, learn this chapter. A proof obligation is the workflow's answer to “how do you know?” — asked once per claim, answered in writing, ranked by strength, and checked by a machine.

    The core idea

    A spec makes claims. The central rule is that no claim may exist without a declared mechanism that keeps it honest. Not “did we test this?” but: for every single thing this spec asserts, what prevents it from being false, and where does that thing live?

    The pipeline names it as its own phase — spec → typed contract → proof obligations → test oracle → implementation → verification — sitting deliberately between what you promise and what you build. That position is the whole trick: obligations are chosen before the implementation exists, so they cannot be retrofitted to whatever the code happened to do.

    Prior art · the term is borrowed, precisely

    “Proof obligation” comes from formal methods — the B method, VDM, Event-B. There, a tool generates obligations mechanically from your model (for each operation, prove it preserves the invariant) and you discharge each one with a proof. The activity is bookkeeping: enumerate everything that must be shown, then show it, and know exactly what remains. verified-scala3 borrows the structure but widens the notion of discharge: a type, a test, a static rule, a proof, or an explicit human review all count — provided the choice is recorded.

    Analogy · the assurance case

    Safety-critical industries file a safety case: a structured argument that a system is acceptably safe, decomposed into claims, sub-claims, and the evidence attached to each (Goal Structuring Notation formalises exactly this). Regulators do not ask “did it pass the tests?”; they ask “show me the argument, and show me which evidence supports which claim”. The proof-obligations table is a small assurance case for one spec — and the F7 check in this chapter is the regulator noticing that claim 3 has no evidence attached to it at all.

    Read the Enforcement column: the mechanism is the compiler. Not a test that checks the property, but a build configuration under which the violating code cannot compile. That is what the top of the ladder looks like.

    The mechanism ladder

    Mechanisms are ranked, strongest first, and the ranking is this workflow's theory of correctness in nine lines:

    1. Type system — invalid state unrepresentable. Cite the type and a compile-negative test.
    2. Smart constructor — rejected at construction. Cite the constructor and a rejection property.
    3. Property / scenario test — falsifiable over a domain, or at a named point.
    4. Compatibility fixture test (Ring 4) — old bytes still decode.
    5. Static rule — Scalafix/WartRemover. Cite the rule.
    6. Formal contract (Ring 6) / model check (Ring 7).
    7. Runtime monitor (Ring 9) — catches it in production, after the fact.
    8. Adversarial review (Ring 8) — a human looking for exactly this.
    9. Manual review — allowed, but must say so explicitly.

    Two things make this ladder load-bearing rather than decorative.

    It mirrors the design ladder. The design artifact ranks invalid-state prevention the same way: impossible to express > rejected by smart constructor > rejected by validator > reaches the evaluator and returns a fallback > silently maps to valid behaviour ◄ forbidden. Choosing an obligation is choosing where on that ladder you defend the claim. When you find yourself writing “property test” for something a type could make unrepresentable, that is a design smell surfacing at spec time — the cheapest possible moment.

    Manual review is legal but never invisible. It propagates to the checkpoint summary (Proof obligations: all enforced / <list of manually-reviewed ones>), so a spec leaning on human diligence says so out loud, to the human approving it, every single time.

    Why it is designed this way · climbing is free later, expensive never

    Mechanisms high on the ladder cost more to design and less to maintain: a type that makes a state unrepresentable never needs re-running, never flakes, never gets muted, and protects code written years later by people who never read the spec. A manual review protects exactly one review. The ladder is an instruction to spend design effort where it compounds — which is also why the workflow makes you name the tier explicitly rather than letting “we'll test it” be the unexamined default.

    How the table gets built

    During the specs artifact, after requirements and properties are written:

    1. Enumerate every claim. Each requirement, each scenario, each property, each invariant, each introduced type constraint, each compile-negative obligation.
    2. Pick the strongest feasible mechanism for each. If Ring 0 can catch it, do not write a test for it.
    3. Name the artifact that will carry it — usually not yet existing. That is fine: it is a commitment the test oracle must fulfil in step 2.
    4. Write the Source in the mandated format so the binding is verifiable rather than plausible.

    The Source format — and the audit that forced it

    This rule exists because of a specific discovery. An audit of real specs across two projects found three incompatible conventions in the Source column:

    Found in the wildResolvable?
    Requirement 1, scenario 1yes — by ordinal
    R2 + Property 2yes — shorthand ordinal
    Requirement + Property: predictors-declaration-order no — names a property but no requirement at all

    The third convention was used consistently across a 33-row table that looked impeccable. Every row had a plausible source, an enforcement mechanism and an artifact. And not one requirement in that spec was provably enforced, because no obligation named a requirement. The old check — “does the table have enough rows?” — passed happily.

    Rule · the mandated Source format
    Requirement: <exact requirement title>   ← PREFERRED: survives reordering
Requirement N   |   RN                    ← allowed; POSITIONAL (warns: W4)

Property: <name>  |  Property N          ← non-requirement sources are
Scenario: <heading>  |  Invariant: <n>      equally valid, but the KIND
Compile-Negative: <what>  |  Temporal: <n>  must be TYPED — the kind word
Criterion: <name>  |  MUST-CONFIRM: <what>  followed by ":" or an ordinal

    Combine with +. A bare Requirement with no identifier names nothing and FAILS F6.

    Note the deliberate asymmetry, which trips people up once: an obligation may legitimately source from a property rather than a requirement. But no requirement may be left unnamed by all obligations. Coverage flows one way only.

    Reachability, not row counting

    This is the conceptual upgrade that F7 represents.

    Old check (weak)

    “The Proof Obligations table covers every requirement.” Verified by counting: 33 rows ≥ 16 requirements, looks complete. Passes on a table where four requirements are mentioned by nothing.

    New check (F7)

    For each requirement, is there at least one obligation that names it? A graph reachability question, answered per requirement. A table with plenty of rows still fails if one requirement is unreachable.

    When F7 was first run against the real specs it reported unenforced requirements in a change that had passed every earlier review — among them “predictor-state is pure immutable data”, a requirement with three scenarios and precisely zero obligations. Not sloppiness: the table's rows were all about behaviour (update is pure, updateAll skips frozen), and the plain data-shape requirement fell through the gap between them. Exactly the kind of thing human review misses because everything present looks right.

    What obligations guarantee — and what they do not

    Being precise here is what separates using this workflow from performing it.

    The guarantee

    If the ledger is complete and each mechanism is real, then every claim in the spec has a named, ranked defence, chosen before implementation, with the weakest defences surfaced to a human at every checkpoint. Concretely, it blocks chapter 1's failure mode: an implementation that satisfies its tests while violating its spec — because what got enumerated was the spec's claims, not the code's behaviour.

    Four things it does not guarantee
    • An obligation is a declaration, not a proof. “Property test” in the Enforcement column does not mean the property is strong, or even non-vacuous. Other machinery covers that: oracle polarity (chapter 6), coverage assertions, and mutation (chapter 7).
    • The Artifact column is unverified. Nothing yet checks that MemorySpec exists, or that it asserts that row. This is the largest remaining hole in the chain.
    • Completeness ≠ correctness of the claims. A perfectly enforced obligation faithfully protects a wrong requirement. That is chapter 1's adequacy row, and only humans supply it.
    • Manual-review rows are escape hatches by design. Legal, visible, load-bearing only as far as the human is.

    Where obligations are enforced

    Five points, which is why the concept survives contact with an agent:

    PointWhat it does
    Authoring (specs)rule 8 mandates the table and the Source format
    Spec lint (mechanical) F4 section present · F6 Source resolvable · F7 every requirement named · W2 row count · W4 positional refs
    Spec lint (judgement) check 12 (declared mechanism), 10 (unreachability claims), 15 (adversarial scenarios)
    Apply step 0 “verify the table is complete… if not, STOP” — implementation cannot begin
    Apply steps 2, 6, 8, 13 oracle table C binds obligations to tests · step 6 re-verifies with zero ❌ · Ring 8 asks whether declared enforcement really enforces · the checkpoint reports the manually-reviewed list to a human
    Why five points and not one

    Each point catches what the others structurally cannot. Authoring catches nothing (it is a rule, not a check). Lint catches format and reachability but knows nothing about code. Step 0 catches an incomplete ledger before effort is spent. Step 2 catches obligations that no test actually implements. Ring 8 catches obligations whose declared mechanism is a fiction. The checkpoint catches everything the machines allowed through, by telling a human what was not mechanically enforced. Remove any one and a specific class of hole opens.

    Deep dive · closing the last linkroadmap

    The artifact column is a string. Checking that MemorySpec exists as a file, and that step 6's Requirement ↔ Test cross-reference names the same suite, is mechanically feasible — the graph tool in chapter 9 already walks requirement → obligation → artifact and could resolve the last hop against the filesystem.

    Two related gaps: property names in Property: X sources are checked as typed but not as existing (a typo passes), and nothing forces a claim about an invalid state to use a tier-1 or tier-2 mechanism when one is available. A rule like “requirements containing never or cannot must be enforced at the type level or justify why not” is the natural next version.

    Two viewpoints on the same table

    Double-entry bookkeeping's power is not arithmetic — it is that every entry must appear twice, in two independent places, so an omission shows up as an imbalance rather than as nothing at all.

    The obligations table is the same device: every claim must appear both as a requirement and as an obligation naming it. F7 is the trial balance. An unenforced requirement is not “a missing test” — it is books that do not balance, and the whole point of the convention is that the imbalance is visible without knowing the business.

    HAZOP and FMEA work by systematically walking a system and asking, for each element, what could go wrong, how it would be detected, and what mitigates it — recording every answer, including “nothing”, because a blank mitigation column is the finding.

    Reading the table this way makes its manual-review rows feel different: they are not weak entries to be embarrassed about, they are accepted residual risk, recorded and signed off. What is dangerous is not a manual row; it is an unrecorded one.
