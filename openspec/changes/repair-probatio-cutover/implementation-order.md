# Implementation Order

Eleven specs, topologically sorted. The proposal's correctness risk is **high**, so **every
spec takes two separate human gates** — no spec qualifies for a combined gate, which
requires `complexity=simple` AND `risk=low`.

## Dependency graph

Spec A depends on spec B when A uses a concept B introduces, or when A's exit criterion
cannot be measured without B.

```
 1 differential-harness-integrity   (no dependencies — introduces the measurement)
 │
 ├─► 2 chain-state-undetermined-fidelity   ─┐
 ├─► 3 completion-witness-refusal          ─┤
 ├─► 4 gate-event-compatibility            ─┤ each needs a trustworthy comparison
 ├─► 5 graph-tool-port ──────────────────► 2 │ (its seam is chain-state's input)
 │                                          │
 ├─► 6 feature-freeze-guard-integrity      ─┤
 ├─► 7 install-tool-surface-parity ───────► 10 (the rename needs the installer)
 ├─► 8 ledger-checkpoint-cutover ─────────► 1 (needs the two new seams)
 ├─► 9 workflow-delivery-hygiene           ─┤
 └─► 11 unported-tool-register ───────────► 5 (the graph tool leaves the register)
```

Edges that force the order:

| Spec | Depends on | Concept or reason |
|------|-----------|-------------------|
| 2 | 1 | Its exit criterion is its suite file at parity with a **genuine** control |
| 3, 4, 6, 9 | 1 | Same — every exit criterion is a comparison |
| 5 | 1, 2 | Introduces the graph the correctness verdict consumes; spec 2 owns that verdict's boundary |
| 8 | 1 | Uses the ledger and checkpoint seams that spec 1 introduces |
| 10 | 7 | The instruction documents are regenerated by the installer, which spec 7 widens |
| 11 | 5 | Exercises "a tool that becomes ported leaves the register" against the tool spec 5 ports |

Specs 3, 4, 6 and 9 are mutually independent; they are ordered by a mix of severity and
size — the two live enforcement holes first, then the cheap wins.

## Standing notes for the apply phase

- **Code intelligence is unavailable.** The semantic endpoint is configured but not
  running (verified during this change's capability-check: the probe reports it
  unreachable and the recorded process id is dead). Apply Steps 0 and 12 use text search
  unless the endpoint is started and re-probed. Two of the recipes that would use it are
  themselves unported predecessors, registered by spec 11.
- **Ring 5 targeting.** The mutation configuration currently pins six files from the
  previous change and carries **no** test filter. Retarget the mutate list per spec before
  each run. The break threshold is zero, so the score must be **read** — the exit code
  never fails the build.
- **Ring 6 invocation.** Call the verification module directly; the convenience alias is
  broken under this sbt version.
- **Specs 1, 6 and part of 8 live in test sources.** Mutation coverage is collected for
  main sources only; use the documented move-to-main-and-back procedure for those runs.
