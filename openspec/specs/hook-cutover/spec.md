## ADDED Requirements

### Requirement: Each bash hook is replaced by a 3-line exec shim pointing to the probatio binary

The cutover SHALL replace each predecessor bash hook script (`gate.sh`, `spec-lint.sh`, `chain-state.sh`, `danger-scan.sh`, `reconcile.sh`) with a 3-line exec shim of the form: shebang (`#!/usr/bin/env bash`), exec line (`exec "<binary-path>" <subcommand> "$@"`), trailing newline. The shim content SHALL be generated by `ShimGenerator.generateShim` (already shipped in `sbt-probatio`). The shim SHALL be byte-identical when regenerated with the same binary path (idempotency). The predecessor script SHALL be preserved at a `.predecessor.bak` path for one swap cycle before deletion, enabling rollback if the oracle regresses.

**Given** a predecessor bash hook script at `openspec/schemas/verified-scala3/hooks/gate.sh` and a resolved probatio binary at `workflow/cli/target/native-image/probatio`
**When** the cutover swaps the gate hook
**Then** `gate.sh` contains exactly 3 lines (shebang, exec, newline), `gate.sh.predecessor.bak` contains the original content, and `ShimGenerator.generateShim(binaryPath)` produces byte-identical content to `gate.sh`

**Rationale**: The 3-line shim is the thinnest possible adapter — it delegates all logic to the binary and introduces no new code paths. The `.predecessor.bak` enables a one-step rollback if the oracle regresses after the swap. Idempotency ensures repeated `probatioGateShim` sbt tasks do not produce spurious diffs.

#### Scenario: The gate shim is generated idempotently

**Given** a resolved binary path `/path/to/probatio`
**When** `ShimGenerator.generateShim` is called twice with the same path
**Then** both outputs are byte-identical: `#!/usr/bin/env bash\nexec "/path/to/probatio" gate "$@"\n`

#### Scenario: The predecessor is backed up before the swap

**Given** a predecessor `gate.sh` with 1700+ lines of bash
**When** the cutover swaps the gate hook
**Then** `gate.sh.predecessor.bak` contains the original 1700+ lines and `gate.sh` contains the 3-line shim

#### Scenario: A changed binary path changes the shim content

**Given** a shim generated for binary path `/old/probatio`
**When** `ShimGenerator.generateShim` is called with `/new/probatio`
**Then** the shim content changes (the exec line references the new path) — the shim tracks the resolved binary

### Requirement: Shims are swapped in dependency order — gate last

The cutover SHALL swap shims in the order defined by `ToolId.swapOrder`: ChainState first, then SpecLint, DangerScan, Reconcile, and Gate last. A swap SHALL NOT proceed for tool N+1 until the oracle is green for tool N (the bats suite passes with tool N substituted at its `*_OVERRIDE` seam). The gate is swapped last because it is the only blocking hook — swapping it before its subcommand dependencies are verified would leave the gate running on unverified subcommands, creating a window where the gate could silently allow blocked edits.

**Given** a seam configuration where ChainState is ported and SpecLint is not
**When** the oracle runs with SpecLint substituted at its seam
**Then** the swap proceeds only if the oracle is green; if the oracle regresses, the swap is aborted and SpecLint remains on the predecessor

**Rationale**: The dependency order prevents a partial cutover where the gate is on the binary but its subcommands are not yet verified. The oracle-green gate is the strangler migration's acceptance criterion — a swap without oracle clearance is an unverified change to a blocking hook.

#### Scenario: ChainState is swapped first

**Given** a fresh cutover with all tools on the predecessor
**When** the cutover begins
**Then** ChainState is the first tool swapped, verified by the `chain-state.bats` oracle at the `CHAIN_STATE_OVERRIDE` seam

#### Scenario: The gate is swapped last

**Given** a cutover where ChainState, SpecLint, DangerScan, and Reconcile are all ported and oracle-green
**When** the cutover swaps the gate
**Then** the gate is the final swap, verified by the `hook-tiers.bats`, `oracle-ordering-lock.bats`, `human-grant-lock.bats`, and `gate-payload.bats` oracles at the `GATE_command` seam

#### Scenario: A regressing swap is aborted

**Given** a cutover where SpecLint is the next tool to swap and the `correctness-invariant.bats` oracle fails with SpecLint substituted
**When** the cutover attempts the SpecLint swap
**Then** the swap is aborted, SpecLint remains on the predecessor, and the abort is recorded in the migration state

### Requirement: Skill-doc updates are atomic with the shim swap

The cutover SHALL update each skill document (`.claude/skills/`, `.pi/skills/`, `.devin/skills/`) that references the predecessor script path to reference the probatio binary path, atomically with the shim swap. The update SHALL be a single `git mv` + content edit commit per tool — the skill doc and the shim swap land in the same commit so a rollback restores both. A skill doc that references a predecessor path after the shim is swapped is a stale reference that would direct an agent to the wrong script.

**Given** a skill doc at `.claude/skills/verified-scala3/SKILL.md` referencing `scanner/spec-lint.sh` and a SpecLint shim swap in progress
**When** the cutover swaps the SpecLint shim
**Then** the skill doc is updated to reference the probatio binary's `spec-lint` subcommand in the same commit as the shim swap

**Rationale**: A stale skill doc directs an agent to the predecessor script, which after the swap is a 3-line shim that delegates to the binary — functionally correct but confusing. The atomic update ensures the skill doc and the shim are always consistent.

#### Scenario: A skill doc is updated atomically with the shim swap

**Given** a skill doc referencing `scanner/chain-state.sh` and a ChainState shim swap
**When** the cutover commits the ChainState swap
**Then** the commit includes both the shim swap and the skill doc update referencing the binary's `chain-state` subcommand

#### Scenario: A stale skill doc is detected

**Given** a skill doc referencing `scanner/spec-lint.sh` after the SpecLint shim has been swapped
**When** the skill-doc linter runs
**Then** the stale reference is reported as a finding (the skill doc directs agents to a shim, not the original script)

## Properties (Ring 3)

### Property: shim-idempotency

**Invariant**: For every resolved binary path, `ShimGenerator.generateShim(path)` produces byte-identical output on every call. The shim content is a pure function of the binary path.

**Generator strategy**: `genBinaryPath` — constructive over absolute file paths with varying depths, special characters (spaces, dots), and trailing slashes. Edge cases: root path, path with spaces, path with dots, empty path (rejected by precondition).

```
property("shim idempotency") {
  for {
    path <- genBinaryPath.forAll
    shim1 = ShimGenerator.generateShim(path)
    shim2 = ShimGenerator.generateShim(path)
  } yield {
    Result.assert(shim1 == shim2)
  }
}
```

### Property: oracle-green-at-every-step

**Invariant**: For every prefix of the swap order, the bats oracle is green when the ported tools are substituted at their seams and the remaining tools are on the predecessor. A swap that would cause the oracle to regress is aborted.

**Generator strategy**: `genSeamConfiguration` — constructive over subsets of `ToolId.swapOrder` that are always prefixes (e.g. {ChainState}, {ChainState, SpecLint}, etc.). Edge cases: empty set (all predecessor), full set (all ported), single-tool prefix.

```
property("oracle green at every step") {
  for {
    config <- genSeamConfiguration.forAll
    oracleResult = OracleGreenCheck.runOracle(config)
  } yield {
    Result.assert(oracleResult.isGreen || oracleResult.isAborted)
  }
}
```

### Property: swap-order-respects-dependencies

**Invariant**: For every swap order, the gate is the last tool swapped. No tool is swapped before all tools earlier in the swap order are ported and oracle-green.

**Generator strategy**: `genSwapSequence` — constructive over valid swap sequences (prefixes of `ToolId.swapOrder`). Edge cases: empty sequence, full sequence, single-tool sequence.

```
property("swap order respects dependencies") {
  for {
    sequence <- genSwapSequence.forAll
  } yield {
    Result.assert(sequence.lastOption.forall(_ == ToolId.Gate) || sequence.isEmpty)
  }
}
```

## Compile-Negative Obligations

| Forbidden Construction | Why | Test |
|------------------------|-----|------|
| A shim that contains logic beyond shebang + exec + newline | A shim with logic is a new code path that bypasses the binary's tested behavior | `assertDoesNotCompile("ShimGenerator.generateShim(path, extraLogic = true)")` — the function takes only a path |
| A `SwapOrder` variant with `Gate` not last | The gate must be swapped last; a swap order with Gate first is a defect | `assertDoesNotCompile("SwapOrder.GateFirst")` — the enum has no `GateFirst` case |

## Formal Contracts (Ring 6)

No formal contracts. The cutover is an operational procedure (file swaps, atomic commits), not an algorithm. The `ShimGenerator.generateShim` function is pure and trivially correct by inspection — the idempotency property test is the enforcement mechanism.
